**A flag that cannot change an output has no failure mode, so it is never blamed — and never
removed.** PGEN's shipping generator recipe read
`ast_pipeline --generate-parser --debug --trace --eliminate-left-recursion`. Every deliverable
parser, locally and in the 11 hosted workflows reaching the recipe through a composite action, was
generated by a command asking the generator to narrate itself. One full regeneration emitted
**6 894 576 244 B** of trace. The artifacts were byte-identical either way — which is exactly why it
survived: nothing it broke ever pointed at it.

**Look for this class where correctness review does not.** A code review asks *does the output
change?* — and here the honest answer is *no*, so the flag passes. The cost lives in a dimension
nobody diffs: what the build **prints**. Three consequences worth separating, because they differ by
an order of magnitude in urgency and conflating them misprices the fix:

- it is a **log-volume** bug, not a runner-disk bug (hosted CI streams step output rather than
  storing it), and a step whose output is truncated is a step whose failure evidence may not survive;
- it is measurably **slower** — bytes written are bytes not spent generating;
- it is **not** an artifact-drift bug, and saying so is what stops the fix being over-scoped.

**Prove the removal with a determinism CONTROL, not just an after-comparison.** Hash the artifacts,
regenerate **with** the flags still on, hash again — *then* remove them and hash a third time.
Without the middle run, "identical" cannot be distinguished from a codegen that is merely stable, and
"different" cannot be distinguished from nondeterminism. Do the per-site A/B with the **same `-o`
path** both times: an output path embedded in a generated artifact makes two different paths produce
two different files for a reason that has nothing to do with the flags.

**Then ask what the flag was actually wired to.** Here, `grep -rn 'config\.debug\|config\.trace'`
returned two writes and zero reads: the `PipelineConfig` fields the flags set are dead, and their
only live path is the trace-verbosity global. So `--trace`'s own CLI help — *"Enable trace mode in
generated parser"* — documented a wire that was not connected. **A stale help string is how a
cost-only flag acquires an imagined benefit** and becomes something people are afraid to touch.

**Move the capability, do not delete it — and look for the knob you already have.** The obvious fix
is a new opt-in variable. Check first: the engine already read `PGEN_TRACE_VERBOSITY`, consulted
whenever no explicit verbosity is passed, and no recipe passed one — so the escape hatch existed and
was strictly more expressive than the boolean that was about to be invented beside it. A second name
for a live mechanism is the prior-art defect, not a convenience.

**Ratchet it or it comes back.** A ruling that lives only in a diff is one revert from undone. The
mechanical form is line-scoped — *no tracked Makefile line invoking the generator may carry
`--debug`/`--trace`* — with controls proving the scope is not over-broad: `--trace-rules` is a live
debug instrument and must pass, a variable **holding** the flags for the opt-in path must pass, and a
comment quoting them must pass. A rule that condemns the escape hatch, or its own explanation,
teaches the next author to waive the gate instead of fixing anything.

⛔ **Removing the noise removes a tell.** The log's sheer volume had been an incidental signal that a
slow regeneration step really ran. Quiet it, and `make` skipping that step — exiting 0 without
regenerating anything — looks the same as doing it. That trap fired during this very measurement
(a `touch` landing 27 ms after the previous write); see
[[feedback_verify_sv_parser_regen_mtime]] and assert mtimes rather than reading the log's size.
