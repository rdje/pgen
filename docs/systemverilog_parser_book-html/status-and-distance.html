PGEN SystemVerilog Parser — Integration Reference

Status and Distance to Done

One question, answered by measurement: how far is this parser from Done, and how much of the corpus passes today?

A status label — Mostly Done, In Progress — says where a family sits on a ladder. It does not say how far it still has to climb, and a reader who only sees the label has no way to tell whether the remaining work is a week or a year. This page publishes the distance behind the label.

This page is DERIVED BY MEASUREMENT. The block below is produced by scripts/report_family_status.sh, which reads the done-bar audit and the corpus census rather than any hand-maintained note. Do not hand-edit it — re-run with systemverilog --markdown and republish; --check docs/systemverilog_parser_book/src/status-and-distance.md refuses when the two disagree. Every field, and the producer that answers it, is declared in rust/test_data/grammar_quality/family_status_block_v0.json.

The three-leg bar, and what it takes to clear it

Done here is not a feeling about maturity. It is a three-leg bar, defined in the main book’s Quality and Closure Model and audited by scripts/audit_done_bar.sh:

  1. Stimuli-generator proof — the family’s own generated samples close the loop with zero residual actionable-target debt.
  2. All our gates — every gate covering the family is green now and is actually invoked by something. A gate nothing invokes is indistinguishable from a gate that does not exist.
  3. All the external test corpus, passing — and a triage gate is not a conformance gate, a characterization is not a pass, and the absence of a corpus is an unmet leg, never an inapplicable one.

How to read the corpus table honestly

The denominator is every row of the SystemVerilog corpus adjudication manifests — not the subset that happens to have been looked at. That choice is deliberate and it is the whole point of the SV-CORPUS-DENOMINATOR doctrine: a defect count published without its denominator is not a claim about the corpus. A row carrying no verdict is not evidence of correctness; it is not evidence of anything, and unknown and clean are different words.

The dark rows are the sharpest edge in the table: the parse failed, and the row’s deferral reason is why nobody has looked at it since. Every one of them is a question the project has not yet asked.

How this page stays true

  • One producer emits both renderings — the brief form reported in the engineer’s completion messages and the thorough block above — so the two cannot tell different stories.
  • --check re-derives the block and diffs it against what is published here, refusing on any difference. Republishing is the only way to change a number on this page.
  • The block is derived from the tracked tree alone. Legs 1 and the green-now half of leg 2 rest on gate artifacts under rust/target/, which is never tracked, so publishing this machine’s reading of them would make the check fail on a fresh clone. Run bash scripts/audit_done_bar.sh to see what the gate artifacts in your tree say.

Release distance — one number, re-derived every release

The question the director asked (2026-09-17): how far is the SV parser from its release, as a number a reader can watch move?

The three-leg bar above says whether the family is Done; the release distance counts what still stands between this tree and that bar, and its history says how fast the count has been falling. items = legs_unmet + bar_rows + open_leaves:

  • legs unmet — the Distance to Done`` line of the derived block above (owned by FAMILY-STATUS-CURRENCY).
  • bar rows — divergence:unexplained_* rows in the three adjudication manifests: the rows the parser must clear on sv_2017, sv_2023 and verilog_2005 (the bar the director’s directive names — “the SV parser shall cleanly pass all of them”).
  • open leaves — todo / active leaves of docs/tasks/SV-CORPUS-GRAD.md plus the todo leaves of docs/tasks/ENGINE-UNIVERSAL-SERVICES.md that SV-CORPUS-GRAD opened (engine work the SV parser owes).

Every figure is derived from the tracked tree by scripts/report_sv_release_distance.sh; nothing here runs a gate, so a fresh clone re-derives the same block. Each parser release appends one row to the history (--record) — and so does a commit outside a release that moves the distance (a leaf closed or opened), under the shipped release’s label, so rows can share a label and the trailing rate divides by distinct releases (SV-CORPUS-GRAD.23, 2026-09-24) — and the doctrine SV-RELEASE-DISTANCE-CURRENCY refuses a commit whose published block or whose history’s last row disagrees with the tree. The history’s commit column names the tree a row was DERIVED from: a row written at a release’s lockstep step carries the release commit’s parent (the release commit does not exist yet when the row is written), a back-filled row the release commit itself. ⛔ What the number is not. The ETA is a trailing-rate ESTIMATE over the last five recorded releases; a structural leg (a corpus conformance gate, the generator proof) is one item that costs more than a bar row; the 38 % of corpus rows with no verdict are an answer-key gap outside items; and an item can be opened by a release as well as closed — the history shows both.
