PGEN SystemVerilog Parser — Integration Reference

The Preprocess→Parse Pipeline

Real SystemVerilog is never parsed raw. A design or verification file is littered with compiler directives — `include pulls in package and macro headers, `define / `ifdef select what is live, and libraries such as UVM are built almost entirely out of macros — so the text the parser must judge is the text that exists after preprocessing. PGEN’s deliverable for SystemVerilog is therefore a pipeline, not a parser alone:

source file(s) ──► SystemVerilog PREPROCESSOR ──► expanded, directive-free text ──► SystemVerilog PARSER ──► AST
                   (macros · `include · `ifdef)          (+ a byte-indexed SOURCE MAP)              (+ verdict)

This chapter describes that pipeline as it ships: what each stage is, the compilation context you hand it, how to run the whole thing in one command, how a rejection is mapped back to the line you wrote, and what the pipeline can and cannot yet do. (The bare parser — a grammar generated from grammars/systemverilog.ebnf — is documented in the rest of this book; the preprocessor’s directive grammar has its own book, the SystemVerilog Preprocessor Parser reference, which is a different deliverable from the expansion stage described here.)

The unit flag is not a convenience. IEEE 1800-2017 §22.5.1 says: “Once a text macro name has been defined, it can be used anywhere in the compilation unit where it is defined. There are no other scope restrictions once inside the compilation unit”, and §3.12.1 makes “all files on a given compilation command line” one compilation unit. A macro defined in the first file of a unit is in force in the last; the pipeline keeps ONE macro table across the list and produces one expansion per file. What `resetall does to that table is nothing — §22.3: “Directives that do not have a default (e.g., `define and `include) are not affected by `resetall.”

One command

# preprocess, then parse — in one process, no scratch file
./rust/target/release/parseability_probe --parse systemverilog hw/ip/uart/rtl/uart.sv \
    --profile sv_2017 --preprocess \
    --include-dir hw/ip/prim/rtl --include-dir stimuli/sv/uvm/uvm-core-2020.3.1/src \
    --symbol SYNTHESIS
# parse_full passed for grammar 'systemverilog' on 'hw/ip/uart/rtl/uart.sv' [preprocessed]

# the AST of the EXPANDED text, same flags
./rust/target/release/parseability_probe --parse-dump-ast-pretty systemverilog top.sv out.json \
    --profile sv_2017 --preprocess --symbol UVM

# a compilation unit: defines.svh first, then the input, one macro table
./rust/target/release/parseability_probe --parse systemverilog dut.sv --profile sv_2017 \
    --preprocess --unit-file defines.svh

--preprocess is SystemVerilog-only (--preprocess with json is refused by name), and the three context flags are refused without it — a context with nothing to apply it to is a typo, not a no-op. The library flags compose unchanged: --lib-out on a package file and --lib-in on the file that imports it work exactly as they do without --preprocess, so a multi-file design is bootstrap files with --lib-out, then the top with --lib-in, each file preprocessed in its turn.

The third code exists so a corpus lane can tell “the language did not accept this” from “the input could not even be expanded” — an unresolved `include, an unterminated `ifdef, an illegal `define. Those are different populations with different owners.

A rejection names the line you wrote

The parser reports positions in the text it parsed — the expanded text, which exists nowhere on disk. Under --preprocess the probe maps the deepest position any branch reached (furthest_position=, the diagnostic that locates a defect; see the debugging chapter of the platform book) back through the preprocessor’s source map and appends [origin=FILE:LINE:COL]:

# a syntax error inside an INCLUDED file names that file and its line
parse_full rejected sample … : Parser did not consume full input at position 12
    [furthest_position=42, +30 bytes deeper than surface position] [origin=inc/bad.svh:3:11]

# a syntax error inside a MACRO EXPANSION names the line of the macro's USE
parse_full rejected sample … : … [furthest_position=38, …] [origin=macro.sv:4:13]

The rule behind the second line: the preprocessor emits one source-map chunk per output line, and an expanded macro’s chunk records the line the macro was used on — the expansion has no line of its own. The column is a character column (a two-byte é before the position counts once). Paths are printed relative to the working directory when they sit under it. A position the map cannot place (an empty expansion) reads origin=unknown rather than nothing.

An opt-in summary line describes the expansion itself:

PGEN_REPORT_PREPROCESS=1 ./rust/target/release/parseability_probe --parse systemverilog f.sv --profile sv_2017 --preprocess
# preprocess: input='f.sv' unit_predecessors=0 include_dirs=0 symbols=0 output_bytes=37 source_map_entries=1 included_files=1 events=5 warnings=0

It is opt-in for the same reason the stack-probe line is: PGEN’s corpus runner captures the probe’s stderr as a per-file measurement column, and an unconditional line would edit a tracked artifact.

What the preprocessor refuses, and why. Since SVPP-EXPANSION.5(g)(h) the expansion stage raises its own errors — the single command reports them as preprocess_failed (exit 3) at the ORIGIN file and line, each carrying the standard’s sentence:

  • E_SVPP_MISSING_MACRO_ARGUMENT — the actual list is shorter than the formals and a formal it leaves unbound has no default (IEEE 1800-2017 §22.5.1: “… error if any of the remaining formal arguments does not have a default specified”; its example `MACRO1 ( 1 ) // ILLEGAL: b and c omitted, no default for c). An EMPTY actual is a different thing and stays legal: present and blank, it is “replaced by nothing” (`MACRO1 ( , 2, )) or takes the default.
  • E_SVPP_EXTRA_MACRO_ARGUMENT — more actuals than formals (“It shall be an error to specify more actual arguments than the number of formal arguments”; `D(,,)).
  • E_SVPP_RECURSIVE_MACRO — a macro expands, directly or through others, to a usage of itself; the message names the chain (`TOP -> `BOTTOM1 -> `BOTTOM -> `TOP). The standard’s exception — “an actual argument to a macro or a default may contain a usage of itself” — is decided by who wrote the usage: every byte of an expansion carries whether the caller wrote it (a source line, or text that came in through an actual or a default) or a macro body produced it. A caller-written usage starts its own expansion context; a body-produced one is checked against the stack of bodies being rescanned. That distinction is what lets OpenTitan nest a `DV_SPINWAIT inside the actual of another (its inner body re-enters a macro the outer expansion still holds) while `define A(x) `B(`A(x)) is still refused: the `A handed to B is A’s own body text.

What the expansion stage rewrites, and what it leaves. Four rules landed with SVPP-EXPANSION.6b.2, each one a sentence of the standard that a corpus row had been failing on:

  • A one-line comment in macro text is not substituted (§22.5.1: “the comment shall not become part of the substituted text”). `define N 21 */* foo */2//foo expands to 21 */* foo */2 — the block comment stays, it is white space to the parser; a string keeps its slashes; a continued line keeps its continuation even when the comment sat on it.

  • Nor is a one-line comment written inside an ACTUAL (SVPP-EXPANSION.5(l), 2026-10-02 — the same sentence, read of the text that gets substituted). `M(a == b // why, exactly<newline>) used to expand to if (!(a == b // why, exactly)) …: the comma inside the comment correctly did not split the argument, but the comment’s text was carried onto the expansion’s single line and commented out the rest of the call — silently (diagnostics=0). Now the comment is dropped up to its line feed when the actual is bound; a block comment stays, and a // inside a string literal is the string’s. OpenTitan writes this in its `DV_CHECK_RANDOMIZE_WITH_FATAL(req, … // TODO … ) calls and in RTL assertion macros: four corpus rows moved fail → pass under the pipeline and none the other way.

  • The paste token joins its sides in an object macro too (§22.5.1: *“A delimits lexical tokens without introducing white space"*): `define YUCK /* garbage */ `` expands to a comment, as a function macro’s substitution always did. In a source line the token stays for the parser to judge.

  • A well-formed `line directive is consumed (§22.12: *“the line directive shall set the line number and file name of the following line"*). The expansion stage is the tool that maintains the current file and line, so `` FILE and __LINE__ `` after it read the assigned location, the event log records the directive (line_directive), and the parser never sees it. A malformed one — a level other than 0, 1 or 2, a missing parameter, a comment on its line — is not this stage's to consume: it passes through, and the parser's own §22.12 production refuses it, so the answer key's must-reject rows on malformed `` line lines keep their verdict under the pipeline. Its parameters may be MACRO USAGES — line new_line_num foo(line) 1 `` — and are expanded first (IEEE 1800-2023 §22.2: *"Macro expansion shall occur within a compiler directive"*; 1800-2017 §22.5.1: a defined text macro *"can be used anywhere in the compilation unit where it is defined"*); the directive is consumed when what they yield is well-formed, and reads exactly as the literal form does (SVPP-EXPANSION.5(n); before, the macros were expanded on a pass-through line and a raw `` line `` reached the parser, which has no production for it inside a procedural block).

  • A comment between the formals of a `define is refused, and the refusal names the clause. §22.5.1 (both editions): “The formal argument names shall be simple_identifiers, separated by commas and optionally white space”; §5.3’s white space is spaces, tabs, newlines and formfeeds, and the standard writes “white space or a comment” where it admits one (§22.4, on the `include line). No sentence of either edition admits a comment there, so `define ARGPAR(a, /* c */ b) and a // after a formal are refused (SVPP-EXPANSION.5(o)); a NEWLINE between formals is white space and is accepted. Three corpus files write the comment form — counted by the lane itself, the rows whose refusal carries this reason — and all three are tool test suites probing the edge: verilator t_preproc.v:277 (its own comment reads “comments MIGHT not be legal”), iverilog macro_with_args.v:17 and sv2v macro_arg_comment.sv:1. No design file in the corpus writes it, so no opt-in tolerance is offered for it.

  • Three readings follow the EDITION of the profile the text will be parsed under (SVPP-EXPANSION.5(p); --profile sv_2023 and sv_2023_tolerant select IEEE 1800-2023, every other profile and the unprofiled reading select 1800-2017).   • Include nesting is bounded by DEPTH, not by a file’s reappearance (SVPP-EXPANSION.5(q); §22.4: “The number of nesting levels for include files shall be finite. Implementations may limit the maximum number of levels to which include files can be nested, but the limit shall be at least 15”). A file that includes itself under a guard (`ifndef INCLUDED / `define INCLUDED / `include "self.sv" / `else …) nests once and is finite — sv2v’s file_line.sv and include_self.sv write that shape — and is read; an unguarded loop is refused when it passes the stage’s limit of 64 levels, and the refusal cites §22.4 and shows the chain’s last steps. Through 1.0.250 any file already on the include stack was refused as an “include cycle”, guarded or not.

  • An escaped identifier is a macro name (SVPP-EXPANSION.5(q); 1800-2017 Syntax 22-2’s text_macro_identifier is an identifier, which A.9.3 makes simple OR escaped; 1800-2023 §22.5.1 says it outright and gives `define \M@CRO3 (a=5, b=0, c="C") … / `\M@CRO3 ( 1 ) as its example). The name is read without its backslash — §5.6.1: “an escaped identifier \cpu3 is treated the same as a nonescaped identifier cpu3” — so `define \escaped is used as `escaped or `\escaped; one terminating white-space character is consumed, so a ( right after it opens the formal list (1800-2023: “only the single white space character terminating the identifier name … shall separate the opening parenthesis from the macro name”); a usage spelled with the backslash is recognised where the run up to white space IS a defined name, so the escaped-quote token `\`" of a macro string keeps its meaning. Through 1.0.250 such a `define was refused as “missing macro name” (iverilog escaped_macro_name.v).

  • A one-line comment inside macro text continues the text when its line ends in backslash-newline, and the comment is dropped — 1800-2023 §22.5.1 says it outright (“If a one-line comment is followed by a backslash and newline character, the comment ends before the backslash and the macro text continues on the next line”), and the 2017 text’s two sentences read together say the same; measured licensed under both profiles and pinned (SVPP-EXPANSION.5(r)). A backslash followed by white space before the newline does NOT continue the macro text on any profile: 2017 “preceded by a backslash”, 2023 “immediately preceded” — the macro ends at that line and the following lines are source. The corpus writes that shape at two sites, both tests (verilator’s own BSSPACE lint-error test is one); no stage option exists for it.

  • Macro text may not leave a string literal open (SVPP-EXPANSION.5(s); §22.5.1 “The text specified for macro text shall not be split across the following lexical tokens: Comments, Numbers, String literals, Identifiers, Keywords, Operators”, with the standard’s own illegal example `define first_half "start of string). The definition is refused, naming the clause; through 1.0.250 it was accepted and the use site glued one string. The scan is the stage’s own (comments and `"…`" macro strings skipped, \" an escape, a backslash-newline inside a string a continuation); a text cut at the end of a number, identifier, keyword or operator is not judged — a stated bound. A formal’s default argument may hold (, ) or , inside a string literal (.5(v)); the list closes at the parenthesis outside every string.

  • A compiler directive cannot be redefined as a macro name, and is a defined name (SVPP-EXPANSION.5(t); §22.5.1 “All compiler directives shall be considered predefined macro names; it shall be illegal to redefine a compiler directive as a macro name”). `define define "illegal" and `define include 1 are refused; `ifdef __FILE__ is true and `ifndef __FILE__ false, so a guarded redefinition is skipped (the ispras 22.13 test’s shape). The set is the edition’s own: IEEE 1364-2005 clause 19 lists nineteen directives; IEEE 1800 adds undefineall (§22.5.3) and __FILE__ / __LINE__ (§22.13), so under the verilog_2005 profile those three are ordinary macro names. Through 1.0.250 both were accepted and a directive name was undefined to the conditionals.

  • A backtick that survives expansion is refused, not handed to the parser (SVPP-EXPANSION.6f). The stage’s post-condition: outside a comment or a string literal, the expanded text carries no backtick except a directive the parser reads. An undefined name is refused as “neither a defined macro nor a compiler directive” (§22.5.1 gives a usage its meaning by substitution — no definition, no derivation; a vendor’s own directive falls under the same sentence), a function-like macro used bare or with an argument list the file never closes under “the parentheses are always required in the macro call” and Syntax 22-3, a `" / `\`" / outside macro text as no token of the language, and an end_keywords `` that closes no region under 1364-2005 §19.11 *"must be paired"*. `begin_keywords regions are rendered, not ignored (SVPP-EXPANSION.8). IEEE 1800-2017 §22.14 lets a block of source select which identifiers are reserved as keywords, from a version of IEEE 1364 or IEEE 1800: inside `begin_keywords "1364-2001" … `end_keywords, logic is an ordinary name. A generated parser reserves one set per PROFILE and cannot switch mid-file, so the expansion stage renders the difference as TEXT — every token the parse profile reserves and the region’s version does not is re-emitted as an ESCAPED identifier:

`begin_keywords "1364-2001"     // the source, as its author wrote it
module top;
  reg [63:0] logic;             // OK: `logic` is not a keyword in 1364-2001
endmodule
`end_keywords

`begin_keywords "1364-2001"     // what the parser is handed
module top;
  reg [63:0] \logic ;           // §5.6.2: "A SystemVerilog keyword preceded by an escape
endmodule                       //  character is not interpreted as a keyword"
`end_keywords

§5.6.1 makes the two spellings the same identifier (“an escaped identifier \cpu3 is treated the same as a nonescaped identifier cpu3”), so nothing about the design changes — only which words the parser may bind as names. What decides the rendering:

  • The profile. --profile reaches this stage on both commands (ast_pipeline --preprocess systemverilog --profile P; --sv-keyword-profile accepted through 1.0.247); under verilog_2005 the parser never reserved logic, so the same region renders nothing. Omitted, the parser’s unprofiled reading is used, which reserves IEEE 1800-2017 Table B.1.
  • The version tables are the LRM’s own — Table 22-1 … Table 22-6 and §22.14.4’s “1364-2001-noconfig” exclusion list — derived from the in-repo standard text and held equal to it on every commit by the SV-KEYWORD-VERSIONS doctrine, never typed by hand.
  • Regions nest (“Each nested pair is stacked”) and run “even across source code file boundaries, until the matching `end_keywords directive or the end of the compilation unit”, so the stack is carried between the files of a --unit-file unit exactly as the macro table is. sv2v’s test/lex/begin_keywords.sv turns on exactly this: inside a "1364-2005" region nested in a "1364-1995" one, task automatic bar; keeps automatic as a keyword while logic becomes a name.
  • It is lexical. A keyword named in a comment, a string literal, a numeric literal, a $-name or an escaped identifier is not a token of the design and is left exactly as written; the source map is re-indexed by the exact byte delta of each rendering, so a rejection still names the line its author wrote.
  • What it cannot do it reports. Text can unreserve a keyword; it cannot reserve a non-keyword. A region naming a version that reserves MORE than the profile raises W_SVPP_KEYWORDS_VERSION_ABOVE_PROFILE and is applied only in the direction text can express; one naming a specifier the profile’s own edition does not define raises W_SVPP_KEYWORDS_VERSION_NOT_IN_EDITION (the parser then refuses the directive); an unpaired `end_keywords raises W_SVPP_UNMATCHED_END_KEYWORDS; and a specifier no version of the standard defines is E_SVPP_UNKNOWN_KEYWORDS_VERSION — §22.14’s own “It shall be an error if an implementation does not recognize the version_specifier”.

Boundaries

  • The expansion engine is hand-written Rust (rust/src/families/systemverilog/preprocessor.rs — the SystemVerilog family’s own component since ENGINE-UNIVERSAL-SERVICES.113, published to the engine as one neutral preprocessing stage, rust/src/preprocessing_stage.rs, which knows nothing of the backtick), not a grammar; its directive structure is separately described by the systemverilog_preprocessor grammar, whose parser does not expand anything. The two are different deliverables and this chapter is about the first.
  • The pipeline preprocesses one compilation unit at a time and parses its last file; a multi-file design still needs the library flags for cross-file declarations.
  • Nothing yet reads a build system’s own context (.core, .f, +incdir+); on the command line the context is what you pass, and in the corpus lane it is derived from the corpus — a shared directory per suite, the nearest candidate per file for a name that exists in several, and a reported tie where the tree cannot decide (a tie between copies of one text is not one); and a directory that would resolve an ambiguous name by the side door is never emitted (.4d).
