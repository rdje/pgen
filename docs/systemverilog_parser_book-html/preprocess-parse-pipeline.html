PGEN SystemVerilog Parser — Integration Reference

The Preprocess→Parse Pipeline

Real SystemVerilog is never parsed raw. A design or verification file is littered with compiler directives — `include pulls in package and macro headers, `define / `ifdef select what is live, and libraries such as UVM are built almost entirely out of macros — so the text the parser must judge is the text that exists after preprocessing. PGEN’s deliverable for SystemVerilog is therefore a pipeline, not a parser alone:

source file(s) ──► SystemVerilog PREPROCESSOR ──► expanded, directive-free text ──► SystemVerilog PARSER ──► AST
                   (macros · `include · `ifdef)          (+ a byte-indexed SOURCE MAP)              (+ verdict)

This chapter describes that pipeline as it ships: what each stage is, the compilation context you hand it, how to run the whole thing in one command, how a rejection is mapped back to the line you wrote, and what the pipeline can and cannot yet do. (The bare parser — a grammar generated from grammars/systemverilog.ebnf — is documented in the rest of this book; the preprocessor’s directive grammar has its own book, the SystemVerilog Preprocessor Parser reference, which is a different deliverable from the expansion stage described here.)

The two stages

StageWhat it doesWhere it livesIts own CLI
Preprocessor (expansion)object-like and function-like macros with defaults, `" stringize, `` token paste, nested expansion, `undef, `__FILE__ / `__LINE__; `include with a search path, cycle and depth guards; `ifdef / `ifndef / `elsif / `else / `endif; a byte-indexed source map, an event log and diagnosticsrust/src/sv_preprocessor.rsast_pipeline INPUT.sv --preprocess-systemverilog
Parserthe generated SystemVerilog parser, profile sv_2017 / sv_2023 / verilog_2005generated/systemverilog_parser.rsparseability_probe --parse systemverilog FILE

The two compose through one type: PreprocessedOutput { text, source_map, events, diagnostics, included_files }. The parser reads text; the source map is what turns a byte offset in that text back into file:line:column of the source.

The compilation context

A preprocessor without a context is a guess. Three things a real front end always knows are the context the pipeline takes, and each has the same spelling on both CLIs:

ContextFlag (both ast_pipeline --preprocess-systemverilog and parseability_probe --preprocess)Meaning
include search path--sv-include-dir DIR (repeatable, ordered)where `include "x.svh" is looked for after the including file’s own directory
predefined macros--sv-define NAME / --sv-define NAME=TEXT (repeatable, ordered)seeded into the macro table before the first line is read, exactly as if `define NAME TEXT stood at the top of the unit; NAME alone defines it with empty text (the meaning a bare `define NAME line has). A predefine is an ordinary definition: `ifdef, `undef and the redefinition policy treat it as one
the compilation unit--sv-unit-file F (repeatable, ordered)the files preprocessed before the input, under the same macro table; the input is the unit’s last file

The unit flag is not a convenience. IEEE 1800-2017 §22.5.1 says: “Once a text macro name has been defined, it can be used anywhere in the compilation unit where it is defined. There are no other scope restrictions once inside the compilation unit”, and §3.12.1 makes “all files on a given compilation command line” one compilation unit. A macro defined in the first file of a unit is in force in the last; the pipeline keeps ONE macro table across the list and produces one expansion per file. What `resetall does to that table is nothing — §22.3: “Directives that do not have a default (e.g., `define and `include) are not affected by `resetall.”

One command

# preprocess, then parse — in one process, no scratch file
./rust/target/release/parseability_probe --parse systemverilog hw/ip/uart/rtl/uart.sv \
    --profile sv_2017 --preprocess \
    --sv-include-dir hw/ip/prim/rtl --sv-include-dir stimuli/sv/uvm/uvm-core-2020.3.1/src \
    --sv-define SYNTHESIS
# parse_full passed for grammar 'systemverilog' on 'hw/ip/uart/rtl/uart.sv' [preprocessed]

# the AST of the EXPANDED text, same flags
./rust/target/release/parseability_probe --parse-dump-ast-pretty systemverilog top.sv out.json \
    --profile sv_2017 --preprocess --sv-define UVM

# a compilation unit: defines.svh first, then the input, one macro table
./rust/target/release/parseability_probe --parse systemverilog dut.sv --profile sv_2017 \
    --preprocess --sv-unit-file defines.svh

--preprocess is SystemVerilog-only (--preprocess with json is refused by name), and the three context flags are refused without it — a context with nothing to apply it to is a typo, not a no-op. The library flags compose unchanged: --lib-out on a package file and --lib-in on the file that imports it work exactly as they do without --preprocess, so a multi-file design is bootstrap files with --lib-out, then the top with --lib-in, each file preprocessed in its turn.

Three outcomes, three exit codes

ExitMeaningWhat you see
0preprocessed and acceptedparse_full passed … [preprocessed]
1preprocessed and rejected by the parserparse_full rejected … [furthest_position=N, …] [origin=FILE:LINE:COL]
3the preprocessor refused the input — the parser never ranpreprocess_failed for grammar 'systemverilog' on '…': … on stderr

The third code exists so a corpus lane can tell “the language did not accept this” from “the input could not even be expanded” — an unresolved `include, an unterminated `ifdef, an illegal `define. Those are different populations with different owners.

A rejection names the line you wrote

The parser reports positions in the text it parsed — the expanded text, which exists nowhere on disk. Under --preprocess the probe maps the deepest position any branch reached (furthest_position=, the diagnostic that locates a defect; see the debugging chapter of the platform book) back through the preprocessor’s source map and appends [origin=FILE:LINE:COL]:

# a syntax error inside an INCLUDED file names that file and its line
parse_full rejected sample … : Parser did not consume full input at position 12
    [furthest_position=42, +30 bytes deeper than surface position] [origin=inc/bad.svh:3:11]

# a syntax error inside a MACRO EXPANSION names the line of the macro's USE
parse_full rejected sample … : … [furthest_position=38, …] [origin=macro.sv:4:13]

The rule behind the second line: the preprocessor emits one source-map chunk per output line, and an expanded macro’s chunk records the line the macro was used on — the expansion has no line of its own. The column is a character column (a two-byte é before the position counts once). Paths are printed relative to the working directory when they sit under it. A position the map cannot place (an empty expansion) reads origin=unknown rather than nothing.

An opt-in summary line describes the expansion itself:

PGEN_REPORT_PREPROCESS=1 ./rust/target/release/parseability_probe --parse systemverilog f.sv --profile sv_2017 --preprocess
# preprocess: input='f.sv' unit_predecessors=0 include_dirs=0 defines=0 output_bytes=37 source_map_entries=1 included_files=1 macro_expansions=1 warnings=0

It is opt-in for the same reason the stack-probe line is: PGEN’s corpus runner captures the probe’s stderr as a per-file measurement column, and an unconditional line would edit a tracked artifact.

What the pipeline does today, measured

The pipeline lane (stimuli/run_pipeline_lane.sh, joined against the raw lane by stimuli/sv/pipeline_vs_raw.py; the tracked report is stimuli/sv/characterization/pipeline_characterization.md, whose identity block names the probe, grammar, parser, context and dumps every number below depends on) parses every source file of a corpus suite through the chain under a context DERIVED from the corpus itself (stimuli/sv/pipeline_context.py: for every `include an includer’s own directory does not satisfy, the one directory that does; an ambiguous name is reported, never guessed — and, since .4c.1, the defines a file’s own driver passes for it: verilator’s t_x.py flags and sv-tests’ :defines: header, a literal value only, applied per file as --sv-define; a value the driver computes at run time and a file several variant drivers configure differently are reported, not guessed. What the preprocessor refuses, and why. Since SVPP-EXPANSION.5(g)(h) the expansion stage raises its own errors — the single command reports them as preprocess_failed (exit 3) at the ORIGIN file and line, each carrying the standard’s sentence:

  • E_SVPP_MISSING_MACRO_ARGUMENT — the actual list is shorter than the formals and a formal it leaves unbound has no default (IEEE 1800-2017 §22.5.1: “… error if any of the remaining formal arguments does not have a default specified”; its example `MACRO1 ( 1 ) // ILLEGAL: b and c omitted, no default for c). An EMPTY actual is a different thing and stays legal: present and blank, it is “replaced by nothing” (`MACRO1 ( , 2, )) or takes the default.
  • E_SVPP_EXTRA_MACRO_ARGUMENT — more actuals than formals (“It shall be an error to specify more actual arguments than the number of formal arguments”; `D(,,)).
  • E_SVPP_RECURSIVE_MACRO — a macro expands, directly or through others, to a usage of itself; the message names the chain (`TOP -> `BOTTOM1 -> `BOTTOM -> `TOP). The standard’s exception — “an actual argument to a macro or a default may contain a usage of itself” — is decided by who wrote the usage: every byte of an expansion carries whether the caller wrote it (a source line, or text that came in through an actual or a default) or a macro body produced it. A caller-written usage starts its own expansion context; a body-produced one is checked against the stack of bodies being rescanned. That distinction is what lets OpenTitan nest a `DV_SPINWAIT inside the actual of another (its inner body re-enters a macro the outer expansion still holds) while `define A(x) `B(`A(x)) is still refused: the `A handed to B is A’s own body text.

What the expansion stage rewrites, and what it leaves. Four rules landed with SVPP-EXPANSION.6b.2, each one a sentence of the standard that a corpus row had been failing on:

  • A one-line comment in macro text is not substituted (§22.5.1: “the comment shall not become part of the substituted text”). `define N 21 */* foo */2//foo expands to 21 */* foo */2 — the block comment stays, it is white space to the parser; a string keeps its slashes; a continued line keeps its continuation even when the comment sat on it.
  • The paste token joins its sides in an object macro too (§22.5.1: *“A delimits lexical tokens without introducing white space"*): `define YUCK /* garbage */ `` expands to a comment, as a function macro’s substitution always did. In a source line the token stays for the parser to judge.
  • A well-formed `line directive is consumed (§22.12: *“the line directive shall set the line number and file name of the following line"*). The expansion stage is the tool that maintains the current file and line, so `` FILE and __LINE__ `` after it read the assigned location, the event log records the directive (line_directive), and the parser never sees it. A malformed one — a level other than 0, 1 or 2, a missing parameter, a comment on its line — is not this stage's to consume: it passes through, and the parser's own §22.12 production refuses it, so the answer key's must-reject rows on malformed `` line `` lines keep their verdict under the pipeline.
  • A function-like macro may open its parentheses on the next line (§22.5.1 requires the parentheses; §5.3 lets white space, newlines included, separate the tokens): `FOO at the end of a line followed by (1, 2) on the next is one invocation.

Four more landed with SVPP-EXPANSION.6b.5, each named by a row of the disposition table:

  • $display is one token. A formal named display is not substituted inside the system task name (A.9.3 system_tf_identifier): `define MACRO_D(display) $display(display); expands to $display("hi"), not $"hi"("hi").
  • A block comment opened on an earlier line is comment text (§5.4), whatever it contains: a `else inside it is not a directive, and the text after an `include filename belongs to the next logical line, so a /* multi-line opened there keeps its close.
  • The coverage-control macros are predefined — IEEE 1800-2017 §40.3.1 says the tool defines `SV_COV_START … `SV_COV_PARTIAL (fifteen names, the clause’s values); a source `define of the same name supersedes.
  • A §34 protected envelope is consumed as opaque. From the `pragma protect line that carries begin_protected to the one that carries end_protected, every line is the envelope’s — key blocks, data blocks, their encoded payload — and none of it reaches the parser; the pragma lines outside the envelope pass through as before. An envelope with no end_protected is refused.

The same slice found a defect no parser could see: the formal-list scanner treated an apostrophe as a string quote — SystemVerilog has none (§5.9) — so `define DV_FCOV_INSTANTIATE_CG(NAME_, COND_ = 1'b1, ARGS_ = ()) had been read as two formals since the scanner’s first commit, a third actual dropped without a word and newARGS_ `` pasted into the legal identifier newARGS_. Only a rule that refuses (extra actuals) made it visible; the fix moved four OpenTitan files to pass.

`begin_keywords regions are rendered, not ignored (SVPP-EXPANSION.8). IEEE 1800-2017 §22.14 lets a block of source select which identifiers are reserved as keywords, from a version of IEEE 1364 or IEEE 1800: inside `begin_keywords "1364-2001" … `end_keywords, logic is an ordinary name. A generated parser reserves one set per PROFILE and cannot switch mid-file, so the expansion stage renders the difference as TEXT — every token the parse profile reserves and the region’s version does not is re-emitted as an ESCAPED identifier:

`begin_keywords "1364-2001"     // the source, as its author wrote it
module top;
  reg [63:0] logic;             // OK: `logic` is not a keyword in 1364-2001
endmodule
`end_keywords

`begin_keywords "1364-2001"     // what the parser is handed
module top;
  reg [63:0] \logic ;           // §5.6.2: "A SystemVerilog keyword preceded by an escape
endmodule                       //  character is not interpreted as a keyword"
`end_keywords

§5.6.1 makes the two spellings the same identifier (“an escaped identifier \cpu3 is treated the same as a nonescaped identifier cpu3”), so nothing about the design changes — only which words the parser may bind as names. What decides the rendering:

  • The profile. --profile reaches this stage (--sv-keyword-profile on ast_pipeline --preprocess-systemverilog); under verilog_2005 the parser never reserved logic, so the same region renders nothing. Omitted, the parser’s unprofiled reading is used, which reserves IEEE 1800-2017 Table B.1.
  • The version tables are the LRM’s own — Table 22-1 … Table 22-6 and §22.14.4’s “1364-2001-noconfig” exclusion list — derived from the in-repo standard text and held equal to it on every commit by the SV-KEYWORD-VERSIONS doctrine, never typed by hand.
  • Regions nest (“Each nested pair is stacked”) and run “even across source code file boundaries, until the matching `end_keywords directive or the end of the compilation unit”, so the stack is carried between the files of a --sv-unit-file unit exactly as the macro table is. sv2v’s test/lex/begin_keywords.sv turns on exactly this: inside a "1364-2005" region nested in a "1364-1995" one, task automatic bar; keeps automatic as a keyword while logic becomes a name.
  • It is lexical. A keyword named in a comment, a string literal, a numeric literal, a $-name or an escaped identifier is not a token of the design and is left exactly as written; the source map is re-indexed by the exact byte delta of each rendering, so a rejection still names the line its author wrote.
  • What it cannot do it reports. Text can unreserve a keyword; it cannot reserve a non-keyword. A region naming a version that reserves MORE than the profile raises W_SVPP_KEYWORDS_VERSION_ABOVE_PROFILE and is applied only in the direction text can express; one naming a specifier the profile’s own edition does not define raises W_SVPP_KEYWORDS_VERSION_NOT_IN_EDITION (the parser then refuses the directive); an unpaired `end_keywords raises W_SVPP_UNMATCHED_END_KEYWORDS; and a specifier no version of the standard defines is E_SVPP_UNKNOWN_KEYWORDS_VERSION — §22.14’s own “It shall be an error if an implementation does not recognize the version_specifier”.

The event log records each directive (keywords_region) with its specifier, how many words the region unreserves and how many tokens it actually rendered.

The deferred population, re-read. The raw answer key is honest about what a one-file parse cannot decide: a must-accept file whose raw parse stops on a macro use, a conditional or an `include is explained by a position test, and a multi-file design file carries no verdict at all. The tracked stimuli/sv/characterization/pipeline_readjudication.md (with its per-row .tsv; SVPP-EXPANSION.6a) joins those rows with what the pipeline actually did to them. Of the 1 434 explained-away must-accept rows, 1 199 parse once preprocessed — the explanation held and the row now testifies for the parser — while 223 still fail in their own text: the explanation was wrong, and each is a defect candidate awaiting a disposition (103 of them are a class header whose base class lives in uvm_pkg). Of the 4 927 chained-only rows, 1 530 are accepted under their derived context, 2 936 still reject in their own file (1 924 on a class … extends header whose base is declared elsewhere — the cross-file fact the library flags exist for), 236 land in an included file and 225 are refused. A chained: outcome is not yet a match: the answer key holds no expected verdict for those rows, and one is derived from the suite’s own convention before the coverage tuple moves. A refuted row keeps that label until someone has looked at it and written down what it is: the tracked stimuli/sv/characterization/refuted_dispositions.tsv carries one line per row looked at — the disposition and its evidence, in the answer key’s own style — and the report splits the refuted rows by it. The dispositions are a closed vocabulary: the base class lives in another file (the library design’s rows), the file’s portable branch is a vendor’s own error stub behind its identity macro, a macro the suite’s driver defines on its command line, a macro a predecessor file of the unit defines, a parser question routed to the corpus tree (legal-looking text the parser refuses, with the clause), a key question (the parser is right to refuse and the row’s expectation is what needs a ruling), an expansion-stage rule not yet implemented. A disposition for a row that has since moved is refused, so the table cannot carry a stale claim. Every refuted row carries one; the report’s refuted_awaiting_disposition is the count still to be looked at.

The library pass (.6d.1). A design is not a bag of files. A file of OpenTitan, black-parrot, VeeR, scr1, friscv or UVM imports typedefs, classes and parameters that a package in another file declares, and the parser only admits such a name where its grammar is fact-gated (a typedef name as a port type, a class name after extends, a parameter name in a range — the store gate of SV-CORPUS-GRAD.13w) once the package’s facts are in scope. The grammar already exports and imports those facts (@export_to_library on package_declaration, @import_from_library on package_import_item; --lib-out DIR / --lib-in DIR). The lane now builds that library before any per-file row runs (stimuli/sv/pipeline_library.py): every package file of the design suites, its import X:: edges read from its preprocessed text, a topological order, each file parsed with its own derived context, the library so far as --lib-in and a private --lib-out, and a passing file’s exports published — at once for a package one file declares, and for a package several files declare (prim_pkg has four, one per vendor) only when every declaring file passed and their fact sets agree; a disagreement is reported, not resolved by guessing which variant the build meant. A rejecting file exports nothing: the engine writes no facts for a rejected parse, so every package importing it stays dark on its names, and the report’s “The library the lane built” table says how many. Then every row runs with --lib-in of the result.

Two thirds of the residue is one fact: the base class of a class … extends lives in another file of the compilation unit (a package the row imports, or a sibling .sv), and the parser’s store gate refuses a base it has not seen declared — the strict reading SV-PARSE-STRICT.2 escaped for net types and not for class bases. That is a cross-file DECLARATION barrier, exactly the one the library flags (--lib-out / --lib-in) exist for; sizing it was the point of the measurement, and the number is now on the table for the leaf that decides how a per-file lane supplies it.

That is not a preprocessing defect: IEEE 1800-2017 A.2.7 gives a const-first class property only the alternative const { class_item_qualifier } data_type const_identifier [ = constant_expression ] ;, and new(…) is not a constant_expression (the local const … order is derivable through data_declaration, which admits a class_new initializer). Every commercial simulator accepts the UVM spelling; PGEN accepted it too until the release of 2026-09-04 made local a reserved word (it had lexed as an identifier and the line mis-parsed into an accept). The policy question — a documented tool-extension arm for a construct the de-facto standard library relies on, versus the letter of Annex A — is open in docs/tasks/SVPP-EXPANSION.md (.5).

Boundaries

  • The expansion engine is hand-written Rust (rust/src/sv_preprocessor.rs), not a grammar; its directive structure is separately described by the systemverilog_preprocessor grammar, whose parser does not expand anything. The two are different deliverables and this chapter is about the first.
  • The pipeline preprocesses one compilation unit at a time and parses its last file; a multi-file design still needs the library flags for cross-file declarations.
  • Nothing yet reads a build system’s own context (.core, .f, +incdir+); on the command line the context is what you pass, and in the corpus lane it is derived from the corpus — a shared directory per suite, the nearest candidate per file for a name that exists in several, and a reported tie where the tree cannot decide.
