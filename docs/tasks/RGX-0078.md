## Goal

Close the **PCRE2-relative** speed gap for the PGEN `regex` parser so RGX's compile-time (which
delegates to PGEN's regex parse) is competitive with PCRE2. Measured baseline (RGX-0073 8-pattern
bench, geomean): PGEN parse is **~360× slower than PCRE2 no-JIT compile, ~85× slower than PCRE2 JIT**.
The absolute `<50µs` target was already met (release 1.1.30, round RGX-0073); the OPEN integration
criterion is the **ratio**.

## ⛔ HARD CONSTRAINT — non-negotiable (director, 2026-07-09, session #73)

**The speed effort SHALL NOT compromise feature accuracy or PCRE2 parity. Any speed optimization that
creates a correctness regression or breaks parity is REJECTED WITHOUT A SECOND THOUGHT — no deliberation,
no "it's only one edge case", no net-win trade-off.** Correctness/parity is a floor, not a variable to
trade against latency. Concretely, an optimization is admissible ONLY if, after it, EVERY correctness
oracle is still green at its pre-optimization value:
- `regex_pcre2_compile_oracle_gate` byte-identical (the PCRE2 corpus verdicts: `2189/1858/285/46` or
  better — never a single new false-accept/false-reject);
- regex cert-coverage `fully_certified` (`UNKNOWN=0`, `spf=0`) at seeds 0/7/42;
- `parse_harness_equivalence_gate` (regex byte-identical interpreter↔generated), `duality_hunt_gate`
  (no new signature), `regex_ast_shape_contract_gate`, and the released-parser pin tests — all green;
- RGX conformance unchanged.

If a candidate is faster but flips ANY verdict / breaks ANY gate, it does not land — full stop. Revert it
and find another lever. This is the operational form of [[feedback_correctness_before_speed]] for the
speed phase itself.

## Methodology (grounded, tools-first)

- **Profile first.** macOS `sample` (or `cargo flamegraph`) on a hot regex parse to pin the actual
  bottleneck — act on the profiled fact, not a guess. Regex's cause is **DIFFERENT from SV's**: SV's
  was the per-rule `SemanticRuntimeState` clone in `with_semantic_runtime_rule_transaction`; regex has
  **no semantic predicates**, so it takes that function's FAST-PATH (skips the clone). So
  `PARSE-TERMINATION.3.1` does NOT help regex — the bottleneck is elsewhere (candidates to confirm by
  profile: packrat memo allocation per rule, `ParseNode`/clone churn, the `FxHashMap` memo, per-char
  overhead vs PCRE2's hyper-tuned bytecode compile + JIT).
- **Candidate techniques (evaluate AFTER profiling, keep iff the geomean improves):** memo/allocation
  tuning; arena / zero-copy `ParseNode`; reducing per-rule overhead; the cut operator / bounded memo
  (Mizushima 2010, PARSE-SOTA B2); avoiding redundant work. **Honest architectural caveat (my take,
  session #73):** PGEN's generated recursive-descent + packrat is inherently heavier than PCRE2's
  hand-tuned NFA/bytecode compiler + JIT. Reaching `<5×` may need STRUCTURAL work (arena allocation,
  a leaner memo strategy, possibly a regex-specific compiled fast path), not just micro-tuning — treat
  this as a research effort with a citation + worked mapping, not trial-and-revert.
- **Resources (in the RGX issue):** the vendorable `pgen_iteration_flow/` harness (standalone C PCRE2
  baselines + a self-contained Rust microbench + a one-shot driver, so PGEN runs the same
  PCRE2-relative measurement without RGX — see `pgen_iteration_flow/README.md`); the PCRE2 test corpus
  (correctness regression + a broader perf corpus).

### Speed technique space (director brainstorm, 2026-07-11 — "JIT/AOT? think out-of-the-box, be creative")

The full menu of speed techniques mapped onto PGEN's actual problem (ONE-SHOT parse of a pattern that
PRODUCES A TYPED AST — = RGX's compile-time). Ranked by leverage × confidence × effort. Correctness floor
NEVER traded ([[feedback_correctness_before_speed]] ⛔) for any of these.

**Framing correction (the useful surprise):**
- **AOT — we ALREADY have it.** Codegen compiles `grammars/*.ebnf → generated/*_parser.rs → rustc/LLVM →
  native machine code`. The generated parser IS AOT-compiled native code (the interpreter is only a debug
  path). So AOT is the FOUNDATION, not a future lever.
- **JIT — does NOT fit the parse phase.** PCRE2's JIT specializes the MATCHER for a pattern and amortizes
  the compile cost over MANY match calls. Parsing a pattern is ONE-SHOT — nothing to amortize (a JIT compile
  would cost more than the single parse it speeds). JIT-the-grammar is redundant with AOT. So "add a JIT"
  is a category mismatch for RGX-0078. (JIT WOULD help RGX's downstream MATCHING phase — but that's RGX's
  job, not PGEN's parse.)

**A) Free AOT wins we are LEAVING ON THE TABLE (cheap, high-confidence, parser-agnostic, correctness-neutral).**
The release build uses cargo DEFAULTS — MEASURED: no `[profile.release]` in `rust/Cargo.toml`, no
`.cargo/config` target-cpu, no PGO. So `lto=false`, `codegen-units=16`, no `target-cpu`. Candidates:
1. **`lto = "fat"` + `codegen-units = 1`** — classic 5-20% on compute-heavy native code, zero code change.
2. **`target-cpu=native`** (or a modern baseline) — SIMD/instruction-set wins for terminal scanning.
3. **PGO (profile-guided optimization)** — ⭐ the AOT-side ANALOG of JIT's benefit: train on the PCRE2 corpus,
   let LLVM re-lay-out hot/cold branches + inlining from the real profile. ~10-20% on branchy parser code.
   This is the honest answer to "can we JIT?" — PGO gives ~half the JIT win (specialized native code from a
   real profile) at AOT time, no runtime cost. Underused, high-value.
   (Caveat: verify determinism + the release binary is what RGX ships; PGO needs a repeatable training run.)

**B) Out-of-the-box — attack the problem, not the inner loop.**
4. ⭐ **Eliminate the parse, don't just speed it (highest real-workload leverage).** RGX compiles MANY
   patterns, MANY of them repeats (across runs / common shapes `\d+` `\w+` `[a-z]+`). A **persistent parse
   cache** (hash pattern string → cached AST, clone on hit) makes every repeat compile ~free — a hashmap
   lookup beats ANY parser. "Don't parse at all" beats every inner-loop tuning. Attacks RGX's ACTUAL cost
   (fixed per-pattern overhead × repetition) more than asymptotics. (An RGX-side cache, or a PGEN embedding-API
   cache.)
5. **Specialized regex fast-path parser.** Regex is THE hot grammar with shallow structure; generate (or
   hand-write) a leaner regex-specific parser that skips the general packrat/semantic-runtime machinery.
   Trades generality for speed on the one grammar that needs it (the "don't use the general engine for the
   hot case" bet). Bigger; correctness proven against the general parser as oracle.
6. **DFA/table-driven token layer.** For the lexical layer (character classes, literal runs), compile a DFA
   like a lexer generator instead of recursive-descent per-char matching. Structural; the algorithmic analog
   of what makes hand-tuned matchers fast.

**C) Structural engine levers (the profile-indicated core work).**
7. **Arena / bump allocation for ParseNode** — attacks the 59% malloc directly (simdjson-style: one arena,
   mass-free). The single biggest allocation lever; parser-agnostic; larger change.
8. **First-set predictive dispatch** — don't try every longest-match branch; skip alternatives that can't
   match the next char. Attacks the backtracking MULTIPLIER, not the per-attempt cost. Deepest algorithmic win.
9. **Per-rule annotation-lookup elision / FxHash** — the ~6% SipHash per-rule lookups (`.3`-adjacent).
10. **SIMD terminal scanning** — character-class / literal runs via SIMD (hyperscan/simdjson-style). Narrow.
11. **Interning + zero-copy** — `&str` slices into the input instead of `String` copies; extend the
    `&'static` rule-name interning (Optim #3) to more transient allocations.

**Sequencing note:** the profile-indicated engine wins (`.3`, then 9 → 7 → 8) come first because they are
measured and parser-agnostic. The build-flag wins (A) are a cheap parallel slice (own leaf) worth grabbing
early since they are ~free. The out-of-the-box bets (4, 5) are the highest real-workload leverage and worth
a design spike — especially the parse cache (4), which may be the single most impactful thing for RGX's
"many patterns" reality. Captured in the book *latency campaign* chapter.

never pays off on tiny inputs, hurting I-cache locality → a net loss. `target-cpu=native` is NOT a universal
win; it can regress branch-heavy code — exactly this case.

### `.5.c` DESIGN — first-set predictive dispatch (parser/EBNF-agnostic, SOUND under longest_match)

**The idea (director, session #94).** On a multi-branch / Or rule, look one char ahead and only evaluate the
branches that could actually begin a match there; skip the rest. "Select the matching branch and commit" — with the
critical soundness refinement below.

**Prior art (research-grounded, [[feedback_research_grounded_sota_no_trial_and_revert]]).** Classic predictive
parsing: LL(1)/LL(k) FIRST / director sets (Dragon book) choose the production without backtracking; ANTLR's
adaptive **ALL(\*)** (Parr & Fisher) builds lookahead DFAs to predict the alternative; re2c/flex dispatch on the
first char via a DFA; PEG "prefix"/first-char guards (Ford). We adopt the **prune** form (FIRST-set director-set),
NOT the full ALL(\*) commit machinery — because our `|` is a longest-match TOURNAMENT, pruning preserves semantics
with none of ALL(\*)'s unbounded-lookahead complexity.

**Soundness contract (the ⛔ HARD CONSTRAINT, byte-identical proof).**
- **PRUNE, don't commit.** For each branch compute `first_set` = a SOUND OVER-APPROXIMATION of the input bytes that
  can begin a match (superset — when uncertain, `ANY`). Before evaluating a NON-nullable branch, peek `c = input[pos]`
  (or EOF); if `c ∉ branch.first_set`, SKIP it. A skipped branch would have failed at char 1 in today's code →
  contributes nothing to the tournament → identical winner. Soundness rests ENTIRELY on `first_set` being a
  superset (never prune a branch that could match).
- **Nullable branches are NEVER pruned** (they can match empty / zero-length regardless of the next char).
- **"Commit" is sound ONLY for a singleton survivor set.** When the FIRST-set filter leaves ≥2 candidate branches,
  the tournament STILL runs among the survivors (longest_match depends on FULL match length, not the first char:
  `atom := "a" | "a" "b"` on `"ab"` — both survive 'a', only the tournament picks `"ab"`). Committing to one there
  = the retired `EarlierAlwaysMatches` unsoundness ([[project_earlier_always_matches_unsound_backtracking]]). For a
  terminal-disjoint regex `atom` the filter collapses ~30 → 1 in the COMMON case, so the "commit" behavior emerges
  automatically and soundly; the multi-survivor case degrades gracefully to a smaller tournament.
- **Conservative (`ANY`, never prune) for:** `.`/any-char, lookahead `&`/`!`, anchors `^`/`$`, `@predicate`/zero-width
  assertions, unresolved refs, case-insensitive/unicode classes not yet modeled, and ANY construct whose first byte
  is not statically known. This keeps soundness absolute at the cost of not pruning those (still correct, just no win
  there). Applies under EVERY `@branch_policy` (a can't-match branch is dead under ordered / priority_first /
  longest_match alike).

**Shape (parser/EBNF-agnostic; NO grammar-name gating; ALL parsers inherit it — [[feedback_features_parser_agnostic_enable_all_parsers]]).**
1. ANALYSIS: a grammar-agnostic FIRST-set pass over the normalized gen-AST (the `--dump-gen-ast` IR) — literal →
   {first char}; char-class → its set; ref → FIRST(ref) transitively to a fixpoint (recursion-safe); sequence →
   FIRST(head) ∪ (FIRST(tail) if head nullable); quantifier `*`/`?` → nullable; everything uncertain → `ANY`.
   Emit a compact per-branch first-set descriptor (byte bitset / small-set) + a `nullable` flag.
2. CODEGEN: for each multi-branch tournament, before a branch's try, emit `if branch_can_start(next_byte) { …existing
   branch eval… }` (skip otherwise). `ANY`/nullable branches emit no guard (always tried). No change to the
   tournament selection logic → longest_match winner identical.
3. This is a CODEGEN change ⇒ regen ALL parsers + verify regen actually happened
   ([[feedback_verify_sv_parser_regen_mtime]] — assert parser-mtime > grammar-mtime / a real behavior delta).

**Acceptance (this leaf):** decisive drift-controlled `regex_perf_probe` geomean before→after (build BOTH release
binaries fat-LTO, measure alternately) showing a real improvement; AND the FULL oracle battery byte-identical at its

#### `.5.c.2` DESIGN REFINEMENTS (session #95, tools-first, before any code — two soundness constraints F1–F4 under-specified)

**R1 — the guard is emitted ONLY for a RULE-TOP-LEVEL `Or`, not a nested one (furthest_position soundness).**
`furthest_position` is bumped ONLY at rule entry (`ast_based_generator.rs:3256` — `if self.position > self.furthest_position`),
NEVER inside `match_string`. A pruned branch fails at char 1 = `parse_start`; the MOST it could push into
`furthest_position` is `parse_start` (reached iff it enters ≥1 child rule there). For a **rule-top-level `Or`**,
`parse_start` == the rule's own entry position, which the rule-entry bump already folded into `furthest_position`
(the wrappers between the bump and the body — memo/transaction/`push_rule_context` — do NOT touch `position`), so
`furthest_position ≥ parse_start` ALREADY ⇒ pruning is furthest-neutral BY CONSTRUCTION. For a **nested `Or`** (after
some matched terminals) `parse_start` can exceed the rule-entry position while `furthest_position` still sits at the
entry (terminals advance `position` without bumping `furthest`); pruning a rule-ref-leading nested branch that today
would enter a child at `parse_start` (bumping `furthest` to `parse_start`) could then LEAVE `furthest` lower ⇒ a
`furthest_position` divergence on reject (the combinator/equivalence gates check it). Restricting to top-level `Or`s
preserves the ENTIRE primary win (regex `atom := literal | dot | … | group` IS a rule body ⇒ top-level; the `.5`
profile's `parse_atom` 7565-sample dominator) and is provably byte-identical incl. furthest. Nested-`Or` pruning is a
future increment (needs the furthest-bump-mirroring worked out, or the `.5.d` lockstep automaton).

#### 🔁 ARENA MODEL DECISION — REVISED to candidate B (session #100, 2026-07-12, director-confirmed) — the derived-`Serialize` oracle is the decider

**The finding that reversed C→B (tool-backed).** The authoritative typed-AST — the exact bytes EVERY differential gate compares (`parse_harness_equivalence` asserts `interp.ast_json == oracle_value`) and `parse_sample_ast_json` returns — is **`serde_json::to_value(&ParseNode)` via `#[derive(Serialize)]`**, at THREE boundary sites: `parser_registry.rs:1083` (`parse_node_to_json`), `parse_harness_interpreter.rs:416`, `parse_harness.rs:457`. NOT `to_json_value` (which is a SEPARATE return-transform-internal path). Consequence:
- **Candidate C (`Sequence(Vec<NodeId>)`) BREAKS the oracle** — the derive would emit BARE INDICES (`{"Sequence":[0,5,12]}`) instead of the nested subtree, and `serde::Serialize::serialize(&self, S)` has NO channel to receive the arena to resolve them. The single most byte-identity-dangerous change possible; directly threatens the #1 immovable correctness floor.
- **Candidate B (`&'arena` references) PRESERVES the oracle FOR FREE** — serde serializes `&T`/`&[T]` byte-identically to `T`, so `#[derive(Serialize)]` on `ParseNode<'input,'arena>` with `Alternative(&'arena ParseNode)`/`Sequence(&'arena [ParseNode])` produces the SAME bytes as today's `Box`/`Vec`. The fragile return-transform code barely changes (children stay dereferenceable; `for node in nodes` still works; construction is `arena.alloc(...)` with no `&mut`/`&` borrow interleave since the arena hands out `&'arena` via interior mutability).

**Drop-correctness (resolved for B).** `ParseContent` carries `String`+`serde_json::Value` (heap `Drop`). Plain `bumpalo` (the only vendored arena, `Cargo.lock:98`) does NOT run `Drop` ⇒ would leak every parse ✗. **`typed-arena`** (small, standard, zero-transitive-deps, the rustc `TypedArena` shape) IS Drop-correct (runs destructors on arena drop) AND hands out `&'arena mut T` from `&self` (build children-then-parents; parents reference children). So B = `typed_arena::Arena<ParseNode<'input,'arena>>`, created at the boundary, passed as `&'arena Arena` to the parser (NOT owned by it ⇒ no self-referential struct), dropped after the boundary serialize walk = mass-free. Memo stores `Option<&'arena ParseNode>` (Copy) ⇒ folds `.5.d.3` sharing for free.

**Cost of B (accepted):** a viral `'arena` second lifetime on `ParseNode`/`ParseContent`/`MemoEntry` and every internal signature touching them — mechanical, COMPILER-CHECKED (a slip is a compile error, never a silent byte diff), and INTERNAL-ONLY (the public boundary returns owned `serde_json::Value`, so `'arena` never leaks to consumers) — plus one new direct dep (`typed-arena`).

**⇒ DECISION: candidate B via `typed-arena`** (director-confirmed, session #100, AskUserQuestion: "B via typed-arena dep (recommended)"). Rationale honors the director's stated criteria (SOTA/signoff/durable/clean/ROCK-SOLID) with correctness-floor primacy: B keeps the byte-identity oracle intact by construction (the dominant consideration), vs C reproducing the oracle by hand. The viral lifetime is the price, paid in compiler-checked mechanical churn, not byte-identity risk. Byte-identity still gated CHEAPLY by the debug oracles before any fat-LTO.

**Revised migration order (candidate B):** (1) add `typed-arena` dep; (2) `mod.rs` — `ParseContent<'input,'arena>`/`ParseNode<'input,'arena>`/`MemoEntry<'input,'arena>` with `&'arena` children + the `'arena` lifetime; `to_json_value` needs NO arena param (children are refs); (3) interpreter (`parse_harness_interpreter.rs`) — build into an `Arena`, mirror the lifetime; (4) codegen (`ast_based_generator.rs`) — the parser struct gains `arena: &'arena Arena<ParseNode<'input,'arena>>`, construction sites `self.arena.alloc(ParseNode{...})`, rule methods return `&'arena ParseNode`, memo stores the ref; (5) thread `'arena` through the walkers until it compiles (mostly signature churn, bodies unchanged); (6) regen 11 parsers + debug oracles (equivalence/combinator/semantic) + fat-LTO measure. #### B. Literature survey (the research-grounded GLL adjudication)

- **GLL** [Scott & Johnson, *GLL Parsing*, ENTCS 253(7) 2010]: generalizes RD to ALL CFGs via descriptors + a graph-structured
  stack (GSS); O(n³) worst case. Its value = handling nondeterminism/ambiguity that would make plain RD exponential or incorrect.
- **Optimized GLL** [Afroozeh & Izmaylova, *Faster, Practical GLL Parsing*, CC 2015 (Iguana)]: a more efficient GSS + optimizations,
  evaluated on highly-ambiguous + real programming-language grammars — the strongest practical GLL.
- **The decisive comparison** [Parr, Harwell, Fisher, *Adaptive LL(\*) Parsing: The Power of Dynamic Analysis*, OOPSLA 2014]:
  ALL(*) — top-down parsing with adaptive lookahead-DFA-cached prediction — "**outperforms general strategies such as GLL and GLR
  by orders of magnitude**" on grammars used in practice (e.g. 3.2MB Java in 360ms vs GLL/GLR-family tools needing GBs + far longer;
  their own data shows the prediction CACHE is what makes it viable — uncached simulation is 100–1000× slower).
- **Worked mapping to PGEN.** Post-`.5.c.2`, PGEN's engine already occupies the ALL(*)-side of this divide: memoized (packrat)
  recursive descent + STATIC k=1 first-set pruning + delta-based winner-only store effects. The regex grammar is deterministic
  (tournament winner selection, no ambiguity — a true `(rule,start,end)` SPPF has nothing to share); the surviving-branch sets after
  first-set pruning are singleton-or-small. GLL's machinery would REPLACE cheap native call/return with heap-allocated descriptors +
  GSS node/edge bookkeeping + SPPF construction on EVERY rule entry — i.e., it ADDS a per-entry constant to the exact ~262ns/entry
  floor that IS the problem, in exchange for removing a backtrack residue measured at **~2.2%** (`rollback_to_named` 1.30% +
  `extract_delta_since` 0.85%). Even the adjacent within-family upgrade (ALL(*)-style adaptive k>1 prediction caching) targets only
  the residual failing probes (~38% of entries on `test` fail, but each fails at char 1 — already first-char-cheap).
- **VERDICT: REFUTED.** Predicted net-NEGATIVE (bookkeeping added ≫ residue removed), against a ≤3% honest ceiling; it cannot land
  under the ⛔ HARD CONSTRAINT (land iff faster + byte-identical). Same adjudication class as `.5.d.3` (premise falsified before
  building — the doctrine working as designed, zero trial-and-revert cost).

#### D. The DERIVED-SCANNER design sketch (director Q&A, session #105, 2026-07-13 — pre-decision, recorded so it survives; NO leaf opened)

Answering the director's "PGEN has no lexer/tokenizer — can we keep EBNF as sole source of truth, stay 100% parser-neutral, AND
benefit from a lexer+tokenizer?" — **YES, by DERIVING the scanner from the grammar, never declaring one**:

- **WHAT'S WRONG with the current model:** the full general-parser apparatus (memo probe + observability + semantic-runtime wrapper +
  tournament + node build + furthest tracking ≈ 262ns) is paid PER RULE ENTRY, and entries go down to single characters (~11/char on
  the bench) — finite-state recognition executed through a general rule engine at ~100× its intrinsic cost.
- **THE FAST SHAPE (layered execution, one grammar):** bottom layer = the grammar's REGULAR subtrees compiled to direct-coded DFAs
  (re2c/Ragel form, ~ns/char, no memo — linearity holds by construction); top layer = structural/annotated/store-gated rules keep the
  existing RD machinery but consume TOKENS ⇒ rule-entry cost per token, not per char.
- **THE CAPABILITY GATE (static, over the gen-AST — parser-AGNOSTIC, never name-gated):** a subtree is scanner-compilable iff
  (1) regular (no ref cycles; iteration via quantifiers only); (2) no outcome/store-affecting directives inside; (3) AST contribution
  reconstructible from matched text (increment 1 = only text-folding token rules — strictest); (4) choice semantics DFA-encodable —
  `longest_match` IS maximal munch (accept-state branch tagging; `a|ab` identical), `ordered`/`priority` = accept-priority tie-break;
  (5) grammar-declared layout policy respected at the boundary. NOT a pre-pass: each scanner is invoked exactly where the cascade
  would have been ⇒ context-dependent tokenization (the reason PGEN is scannerless) preserved BY CONSTRUCTION.
- **DUALITY untouched** (execution-only change; stimuli generation walks the same EBNF). **Pre-registered risks (pause-and-agree):**
  (R-i) rule-participation TESTIMONY must be synthesized by the fused scanner (cert coverage + contract gates consume it);
  (R-ii) furthest_position parity on rejection; (R-iii) gate breadth per grammar unknown until the census.
- **ROAD (the proven method):** STEP 0 = mechanical FUSIBILITY CENSUS over all shipped grammars (the ceiling, measured BEFORE any
  build — the `.5.d.3`/`.5.e` discipline) → DFA construction (Thompson/subset over the gen-AST; FIRST-set machinery already computes
  on this IR) → codegen emission (identical folded AST + testimony + furthest) → byte-identical increments (leaves → chains →
  keyword/alternation sets → deeper), interpreter stays UNFUSED as the fresh-walking reference oracle (the `.5.g` pointed-oracle

  return annotation + semantic annotation and still use a lexer and tokenizer in the background"* — satisfied by construction:
