## Goal

Close the **PCRE2-relative** speed gap for the PGEN `regex` parser so RGX's compile-time (which
delegates to PGEN's regex parse) is competitive with PCRE2. Measured baseline (RGX-0073 8-pattern
bench, geomean): PGEN parse is **~360× slower than PCRE2 no-JIT compile, ~85× slower than PCRE2 JIT**.
The absolute `<50µs` target was already met (release 1.1.30, round RGX-0073); the OPEN integration
criterion is the **ratio**.

## ⛔ HARD CONSTRAINT — non-negotiable (director, 2026-07-09, session #73)

**The speed effort SHALL NOT compromise feature accuracy or PCRE2 parity. Any speed optimization that
creates a correctness regression or breaks parity is REJECTED WITHOUT A SECOND THOUGHT — no deliberation,
no "it's only one edge case", no net-win trade-off.** Correctness/parity is a floor, not a variable to
trade against latency. Concretely, an optimization is admissible ONLY if, after it, EVERY correctness
oracle is still green at its pre-optimization value:
- `regex_pcre2_compile_oracle_gate` byte-identical (the PCRE2 corpus verdicts: `2189/1858/285/46` or
  better — never a single new false-accept/false-reject);
- regex cert-coverage `fully_certified` (`UNKNOWN=0`, `spf=0`) at seeds 0/7/42;
- `parse_harness_equivalence_gate` (regex byte-identical interpreter↔generated), `duality_hunt_gate`
  (no new signature), `regex_ast_shape_contract_gate`, and the released-parser pin tests — all green;
- RGX conformance unchanged.

If a candidate is faster but flips ANY verdict / breaks ANY gate, it does not land — full stop. Revert it
and find another lever. This is the operational form of [[feedback_correctness_before_speed]] for the
speed phase itself.

## Methodology (grounded, tools-first)

- **Profile first.** macOS `sample` (or `cargo flamegraph`) on a hot regex parse to pin the actual
  bottleneck — act on the profiled fact, not a guess. Regex's cause is **DIFFERENT from SV's**: SV's
  was the per-rule `SemanticRuntimeState` clone in `with_semantic_runtime_rule_transaction`; regex has
  **no semantic predicates**, so it takes that function's FAST-PATH (skips the clone). So
  `PARSE-TERMINATION.3.1` does NOT help regex — the bottleneck is elsewhere (candidates to confirm by
  profile: packrat memo allocation per rule, `ParseNode`/clone churn, the `FxHashMap` memo, per-char
  overhead vs PCRE2's hyper-tuned bytecode compile + JIT).
- **Candidate techniques (evaluate AFTER profiling, keep iff the geomean improves):** memo/allocation
  tuning; arena / zero-copy `ParseNode`; reducing per-rule overhead; the cut operator / bounded memo
  (Mizushima 2010, PARSE-SOTA B2); avoiding redundant work. **Honest architectural caveat (my take,
  session #73):** PGEN's generated recursive-descent + packrat is inherently heavier than PCRE2's
  hand-tuned NFA/bytecode compiler + JIT. Reaching `<5×` may need STRUCTURAL work (arena allocation,
  a leaner memo strategy, possibly a regex-specific compiled fast path), not just micro-tuning — treat
  this as a research effort with a citation + worked mapping, not trial-and-revert.
- **Resources (in the RGX issue):** the vendorable `pgen_iteration_flow/` harness (standalone C PCRE2
  baselines + a self-contained Rust microbench + a one-shot driver, so PGEN runs the same
  PCRE2-relative measurement without RGX — see `pgen_iteration_flow/README.md`); the PCRE2 test corpus
  (correctness regression + a broader perf corpus).

### PROFILE RESULTS (session #90) — tool-backed WHY + WHERE

**Method:** `sample <pid> 12 -mayDie` (macOS profiler, 1 ms) on release binaries: regex via
`regex_perf_probe` hot loop; json via a single `parseability_probe --parse json big.json` (740 KB,
4000-object array); vhdl via `--parse vhdl big.vhd` (146 KB, 1500 entities). Raw sample dumps +
`profile_all.sh` in the session scratchpad.

**REGEX self-time (9630 leaf samples, categorized):**
- **malloc / free / memops — 5719 (59.4%)** ← the dominant SYMPTOM (`_xzm_free` 1729, `_xzm_xzone_malloc`
  536, `_malloc_zone_malloc` 491, `_free` 365, `memmove` 449, `memset`/`__bzero` 438, `___rdl_alloc` 209…).
- semantic-runtime (rollback + per-rule annotation lookups) — 668 (6.9%)
- SipHash / hashmap — 576 (6.0%) (`sip::Hasher::write` 321 + `hash_one` 103 + `reserve_rehash` 90 + insert 48)
- string formatting — 419 (4.4%) (`format_inner`/`fmt::write`/`String::write_str`/`Formatter::pad`/`Display::fmt`)
- clone / drop — 144 (1.5%)

**Call-graph attribution of the 59% malloc (subtree sample sums):**
- **`SemanticRuntimeState::rollback_to_named` = 2285 samples ≈ 24% of total** ← the SINGLE largest
  allocation source. Called on every failed speculation (backtrack). Its children show
  `Vec::spec_from_iter_nested::from_iter` + `_malloc_zone_malloc` + `__bzero` = the **`self.scopes =
  active_chain.iter().map(..).collect()` rebuild (`semantic_runtime.rs:2804`)** and the
  `active_chain_snapshot.clone()` (`:2793`), both run UNCONDITIONALLY per rollback.
- `HashMap::insert` (181+45+12+5) + `reserve_rehash` (133+21+4) — memo + annotation-table churn.
- `ParseContent::to_json_value` 69, `drop_in_place<ParseContent>` 64, `extract_delta_since` 60,
  `push_rule_context` 33.

**SYSTEMIC — CONFIRMED across grammars (shared engine code, not a regex path):**
- **json** (predicate-free): `create_contextual_error` 174 (the backtrack-path error-construction analog
  of regex's rollback/format strings), `RecursionGuard::check_cycle` 130 (shared; also in regex 43),
  the same malloc family, `sip::Hasher::write` 18, `BTreeMap`/`ParseNode`/`String` clones.
- **vhdl** (predicate-CARRYING; small sample — parse finished fast): top frames still `_xzm_free`/`_free`/
  `memmove`/`malloc` + `sip::Hasher::write` 6 + `String`/`BTreeMap` clones — same shape.

**REFUTED (profile beats inference — [[project_uvm_memory_not_the_memo]]):** the "per-parser construction
rebuilds the annotation table ⇒ ~160µs floor" hypothesis. Call graph: `RegexParser::new` ≈ **~70 samples
(~0.7%)** vs `parse_full` **9584**. Construction is NEGLIGIBLE; the PARSE dominates. The 163µs floor for
`"test"` is the per-character `atom`-tournament (each char tries ~30 atom alternatives under
`longest_match`, most backtrack — each failed speculation pays the rollback allocation above). This
CONFIRMS the reframing's hypothesis #1 (every-branch tournament) as the DRIVER and #2 (per-speculation
overhead) as the COST, and correctly kills the construction red herring.

**Ranked systemic levers (profile-indicated, for `.3`+):**
1. **Backtrack/rollback allocation (~24%)** — `.3` gates the unconditional `active_chain` clone + `scopes`
   `.collect()` in `rollback_to_named` on scope-state-changed. No regen; correctness-neutral.
2. **Per-rule SipHash annotation-table lookups** (`needs_raw_post_capture_for_rule`/`_final_`/
   `pre_predicates_for_rule`/`has_rule` ≈ 330 + hashing 560): every rule entry SipHash-looks-up a
   mostly-empty table for predicate-free grammars. Candidate: FxHash the table (Optim #6 precedent) and/or
   codegen-elide the lookups for annotation-free rules.
3. **Reduce per-speculation allocation churn** (ParseContent/Vec per branch attempt) — the longest_match
   tournament trying every atom alternative per char is the structural driver; first-set predictive
   dispatch is the deeper (higher-risk, later) lever.
4. **Backtrack-path trace strings** — the generated `try_parse` Err arm builds `entry.0.to_string()` +
   `format!("{} (try_parse Err)")` per failed speculation for a `rollback_to_named` context that is only
   consumed when facts/scopes were actually rolled back OR trace is on. Codegen change (regen) — sequenced
   after the no-regen wins.
