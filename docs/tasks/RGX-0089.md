## Goal

Fix `PGEN-RGX-0089` (downstream report
`/Users/richarddje/Documents/github/rgx/pgen-issues/PGEN-RGX-0089.yaml`, artifacts
`…/artifacts/PGEN-RGX-0089/`): PGEN rejects `(?[\b])` and `(?[[\b]])` — and the
shipped RGX fixture `\A(?[\a | \b | \e | \f])+\z` — although PCRE2 10.47 ACCEPTS
all of them and matches U+0008 (backspace). Ordinary-class `[\b]` and the
body-level word-boundary `x\b` are unaffected. RGX probed the whole extended-class
escape family: **`\b` is the SOLE regressed escape**. This is the sole
parse-verdict blocker for RGX's adoption of the RGX-0078 closure pin.

## Root cause (tool-backed, session #188)

- **Regressing commit found by bisecting the grammar surface**: `git log -S
  'simple_escape_letter_strict' -- grammars/regex.ebnf` → `40202cb0`
  (`PGEN-REGEX-PCRE2-0011`, `REGEX-PCRE2-FIDELITY.3.13`, **release `1.1.82`**) —
  exactly brackets the reporter's "green on 1.1.81, red in the 1.1.83→1.1.106
  window".
- `.3.13` re-spelled `simple_escape`'s letter component as a POSITIVE enumeration
  (`simple_escape_letter_strict`, `grammars/regex.ebnf:1347`) that deliberately
  EXCLUDES the 7 escape-anchor letters `A B G K Z b z` — sound at PATTERN-BODY
  level, where those spellings are anchors owned by the `anchor` rule (and where
  the change fixed quantified-anchor rejection, PCRE2 err 109). The slice comment
  called the drop "behavior-invisible" — true only where `anchor` is reachable.
- Inside the extended class it is NOT: `extended_class_element =
  extended_class_nested | escape | extended_class_regular`
  (`grammars/regex.ebnf:2140-2142`) routes escapes through the generic body
  `escape` rule; `anchor` has no derivation there, and `extended_class_regular`
  cannot match a backslash. So `\b` inside `(?[...])` lost its ONLY derivation.
  Ordinary classes are unaffected because they use the separate
  `class_simple_escape` family whose letter set keeps `b`.
- **Trace-proven** (`PGEN_TRACE_VERBOSITY=debug --trace-rules
  extended_class_element,escape,escape_unit,simple_escape` on `(?[\b])`):
  at position 3, `extended_class_element` branch 2/3 (`escape`) enters, matches
  `\`, then `escape_unit` fails ALL branches at position 4 (`❌ Exiting rule
  'escape_unit' with error: Backtrack { position: 4 }` — `b` underivable),
  branch 2 fails, the element fails, and the pattern rejects at position 0
  ("Parser did not consume full input at position 0" — reproduced with
  `parseability_probe --parse regex` on pin HEAD).
- Why no gate caught it for ~23 releases: grammar-derived stimuli can never emit
  a derivation the grammar LACKS (the rejects-valid blind spot — director
  observation recorded in
  `docs/decisions/feedback_stimuli_gen_rejects_valid_blindspot.md`, action
  deferred), and the PCRE2 conformance corpus has no `(?[\b])` cell.

## Fix design (fix-hierarchy level: GRAMMAR — annotations/EBNF, no engine change)

`grammars/regex.ebnf`: restore the class-context meaning of `\b` with a
dedicated POSITIVE branch reachable ONLY from extended-class content:

```
extended_class_element = extended_class_nested
                       | escape
                       | extended_class_backspace_escape
                       | extended_class_regular
extended_class_backspace_escape = "\\b" -> {type: "escape", kind: "shorthand", char: "b"}
```

- PCRE2-faithful by construction: `\b` is the classic dual-meaning escape
  (assertion in the body, backspace in class context); the dedicated branch IS
  the grammar encoding of that duality, exactly parallel to
  `class_simple_escape` keeping `b` for ordinary classes.
- NOT added to `escape_unit`/`simple_escape` — that would re-admit body-level
  `\b` as a shorthand and regress the `.3.13` quantified-anchor fix (`\b*` must
  stay REJECT err 109).
- Generation-faithful (the `.3.13` duality law): a positive literal branch, no
  lookahead — the stimuli generator can emit and witness it (cert gains one
  rule; `fully_certified` must stay true at `spf=0`).
- `(?[[\b]])` nested form is covered for free (`extended_class_nested` recurses
  into `extended_class_content`).
- Tournament safety: for input `\b` exactly one branch derives (the new one —
  `escape` has no derivation, `extended_class_regular` can't match `\`); for
  every other escape the new branch can't match. No AST change for ANY
  currently-accepted pattern.

Bookkeeping (behavior-CHANGING rejects-valid fix, the REGEX-0098/`.4.11`
