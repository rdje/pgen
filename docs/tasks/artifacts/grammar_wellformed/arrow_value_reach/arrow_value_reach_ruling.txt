────────────────────────────────────────────────────────────────────────────────────────────
1. THERE ARE THREE ROUTES, NOT TWO
────────────────────────────────────────────────────────────────────────────────────────────
  route 1  lambda_expression   LHS is a `lambda_parameter` — an identifier, a `[a,…]`/`{a,…}`
                               destructuring pattern, or a parenthesised parameter list;
                               the RHS is then an unrestricted `annotation_value`
  route 2  implication_expr    BOTH sides are `logical_or_expr`
  route 3  function_type       LHS is a parenthesised `type_reference` list, RHS is a
                               `type_reference` — the ONLY route whose RHS must be a type

  Route 3 is distinguishable, not a re-description of 1 or 2: `(Foo<Bar>) => Baz` parses and
  `(Foo<Bar>) => 1` does not. No lambda or implication reading produces that pair.
  → `arrow_route_probes.sh`, 19 probes, all expectations held; `arrow_route_probes.txt`.

  → `build_own_corpus.sh` (byte-reproducible), `own_corpus_selfreject_head.txt`.

  ROOT CAUSE OF THE THREE ROWS, and why they cannot recur.
  The pristine corpus was generated by the pre-(a+) grammar (`dcc2e2d8`), whose map entry read

      map_entry := annotation_value /\s*/ "=>" /\s*/ annotation_value

  Under that rule the stimuli generator could derive the KEY as a `lambda_expression` — `W => %RXCy`
  — and then append the map's own arrow and value, emitting `W => %RXCy => 72e10`. The parser can
  never re-derive that reading, because `annotation_value` reaches `identifier_literal` through
  `primitive_value` first and takes `W` alone. `H.16.6b` replaced that key with `map_key`, which by
  construction excludes every arrow-consuming reach, so no key the generator builds can carry an
  arrow any more. ⇒ **the producer of all three rows was removed one leaf before this one opened.**
  The three rows are PRE-(a+)-VINTAGE CORPUS RESIDUE: rows the fixed generator cannot emit.
  This is `H.16.6c`'s own lesson, applied to `H.16.6c`'s own residual.

3. AND THE REMAINING ASYMMETRY IS CORRECT, NOT A HOLE
────────────────────────────────────────────────────────────────────────────────────────────
  ARROW-POSITION-CENSUS at HEAD — 23 operand shapes × 5 positions, 115 verdicts:
      all 23 are legal map KEYS · all 23 are legal plain VALUES · all 23 are legal arrow RHS
      13 may sit LEFT of an arrow in a value; 10 may not
      `key_ok_but_value_arrow_lhs_rejected = 10`
  The 10: string · single-quoted · `[1]` · `{a: 1}` · `#{1}` · map · symbol-ref · path · URL ·
  generic type.

  ⛔ THE LEAF'S FRAMING — "the value position accepts too LITTLE; the union does not cover
     `any => any`" — ASSUMES a fourth arrow construct exists to admit. There is none. A `=>` in a
     value is a lambda, an implication or a function type, and each has a declared operand
     language: a string is not a lambda PARAMETER, not a logical OPERAND and not a parenthesised
     TYPE LIST. `{ k => "s" => 1 }` has no reading, so rejecting it is the correct verdict.
  ⭐ The KEY may be any of the 23 for the symmetric reason: a key is followed by the map's OWN
     arrow, so it is an operand of nothing. `map_key` is broader than the value-arrow LHS language
     because it answers a different question — not because one of them is wrong.
  ⭐ This is the H.16.6d lesson re-applied: the apparent trade-off was a consistency question the
     artifact had already answered. The book's own sentence — "`=>` … in THREE roles: the
     implication operator, the lambda arrow and the function-type arrow" — IS the answer.
