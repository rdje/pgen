0. WHAT WAS RUN, AND WHY IT IS NOT LITERALLY `regenerate_generated_parsers`
------------------------------------------------------------------------------
The measured sequence is that target MINUS its first step, `regex_parser_bootstrap`,
whose unconditional `cargo build --features ebnf_dual_run` downgrades
`rust/target/debug/ast_pipeline` and makes the documented recipe fail in 15 s on any
WARM tree. That is `CI-PARITY-GATE-ROT.30`, a separate open leaf, and this leaf does not
fix it. Everything after that step is invoked exactly as the target invokes it:

    make -C rust SHELL=/bin/bash annotation_parsers
    for f in json regex systemverilog systemverilog_preprocessor vhdl \
             rtl_const_expr rtl_frontend; do make -C rust SHELL=/bin/bash focus_$f; done

Each `generated/<f>.json` is `touch`ed first so every generator invocation actually
fires on a warm tree (the parser rules depend on their JSON; the JSON rules depend on
the .ebnf, so touching the JSON re-runs codegen without re-running the frontend).
Harness: `rust/target/ci_parity_rot31/measure_regen.sh` (untracked, on the repo volume),
run under `scripts/run_with_memory_guard.sh --budget-mb 16384`.

3. WHY IT CANNOT AFFECT AN ARTIFACT (the structural half)
------------------------------------------------------------------------------
`--debug` / `--trace` reach the pipeline through exactly two paths:

  rust/src/main.rs:936-938  resolve_trace_verbosity(args.verbosity, args.debug, args.trace)
                            -> set_global_trace_verbosity(...)   [gates the pgen_trace! macros]
  rust/src/main.rs:1097-98  config.debug / config.trace

and the second is dead:

  $ grep -rn 'config\.debug\|config\.trace[^_]' rust/src/
  rust/src/main.rs:1097:    config.debug = args.debug || trace_verbosity >= TraceVerbosity::High;
  rust/src/main.rs:1098:    config.trace = args.trace || trace_verbosity >= TraceVerbosity::Debug;

Two writes, zero reads. ⇒ `--trace`'s own CLI help, "Enable trace mode in generated
parser (detailed debug logging)" (rust/src/main.rs:441-443), describes a wire that is
not connected: the `trace_enabled()` gates inside a generated parser are emitted
unconditionally and consult the RUNTIME verbosity, not the generator's.

------------------------------------------------------------------------------
4. THE TRACE IS OPT-IN, NOT DELETED — and no new knob was invented
------------------------------------------------------------------------------
`resolve_trace_verbosity` consults `PGEN_TRACE_VERBOSITY` / `PGEN_VERBOSITY` whenever no
`--verbosity` is passed, and no recipe in `rust/Makefile` passes one. So the engine's
existing knob already IS the opt-in, and adding a `PGEN_GENERATOR_TRACE` beside it would
have been a second name for a live mechanism (`DESIGN-PRIOR-ART`).

Measured on `focus_json`, warm, one regeneration each:

  (default, quiet)                          366 B
  PGEN_TRACE_VERBOSITY=high          16 003 019 B     <- the old RUST_GENERATOR_BOOTSTRAP level
  PGEN_TRACE_VERBOSITY=debug         21 955 687 B     <- the old RUST_GENERATOR level
                                                         (cf. 21 955 519 B measured direct
                                                          from `--debug --trace` in §2)

⛔ THE `high` ROW READ **62 B** ON ITS FIRST ATTEMPT AND THAT WAS NOT A RESULT.
   `make` had judged `generated/json_parser.rs` up to date: the preceding run wrote it at
   21:49:16.676 and the `touch` landed at 21:49:16.703, 27 ms later. The number was kept
   only because it was implausible — this is verbatim the trap
   `docs/decisions/feedback_verify_sv_parser_regen_mtime.md` names, "make exiting 0 means
   make ran, NOT that the parser was regenerated", observed live while measuring.
