# THE COLD-CLONE BOOTSTRAP IS BROKEN, AND IT WAS BROKEN BY A ONE-LINE FIX BELIEVED INERT
# Measured 2026-08-21 while ENGINE-UNIVERSAL-SERVICES.43 needed a full regeneration.
# ⛔ This file exists because the FIRST version of this finding was WRONG and the correction
#    is the point: I called it "a longstanding hole that only works because generated/ is
#    never empty". The repository's own records refute that, and resolving the contradiction
#    produced a sharper and dated finding.

## THE SYMPTOM — one error, reproduced twice

  From a tracked-files-only tree (`generated/` empty), `make -C rust regenerate_generated_parsers`
  seeds `generated/ebnf.rs`, generates the annotation pair, and then dies:

    error[E0425]: cannot find function `active_grammar_profile` in module `crate::parser_registry`
       --> src/parse_harness_equivalence.rs:332:50
    note: found an item that was configured out
       --> src/parser_registry.rs:443:8
    435 | #[cfg(any(has_generated_systemverilog_parser, has_generated_regex_parser))]
    error: could not compile `pgen` (lib) due to 1 previous error

  Reproduced (1) by the full cold run itself (logs/regen2.log — EXACTLY ONE error, and zero of
  any other class), and (2) by a CONTROLLED probe that removes only the two gating artifacts and
  builds into a SEPARATE target dir so the working build cache is untouched:

    mv generated/systemverilog_parser.rs generated/regex_parser.rs <hold>/
    CARGO_TARGET_DIR=rust/target/coldprobe cargo check --manifest-path rust/Cargo.toml \
        --features "generated_parsers ebnf_dual_run" --lib
    => the same single E0425.

## THE MECHANISM — a circular dependency across THREE files, none of them recently touched

  rust/src/lib.rs:36              #[cfg(all(feature="ebnf_dual_run", feature="generated_parsers"))]
                                  pub mod parse_harness_equivalence;      <- gated on FEATURES
  rust/src/parser_registry.rs:435 #[cfg(any(has_generated_systemverilog_parser,
                                            has_generated_regex_parser))]
                                  pub fn active_grammar_profile(...)      <- gated on ARTIFACTS
  rust/src/parse_harness_equivalence.rs:332  calls it UNCONDITIONALLY

  rust/Makefile                   regex_parser: $(REGEX_JSON) $(RUST_AST_PIPELINE)
                                  $(RUST_AST_PIPELINE): ... ; cargo build \
                                      --features "generated_parsers ebnf_dual_run" --bin ast_pipeline

  => the target that CREATES the first gating artifact has, as a prerequisite, a build that
     cannot succeed until one of them already exists.

## THE CONTRADICTION I HAD TO RESOLVE, NOT DISMISS

  .github/actions/regenerate-parsers/action.yml says, in its own words:
      "Measured cost from a bare tracked tree: ~258 s."
  committed 11fcb45c, 2026-07-28, CI-PARITY-GATE-ROT.4.

  And the call site that fails is OLDER than that:
      f2ae3d8f 2026-07-05  PARSE-HARNESS.5.1 — adds active_grammar_profile AND its call site.

  So .4 measured a SUCCESSFUL cold regeneration on a tree that already contained the call.
  My "longstanding hole" reading is therefore REFUTED by the repository's own record.

## WHAT ACTUALLY HAPPENED — one line, 14 days after .4 measured the path green

      0099d0d3  2026-08-11  CI-PARITY-GATE-ROT.24 slice 2
      "the canonical ast_pipeline rule now OWNS its path's capability, so 21 dependants can no
       longer rebuild an under-featured binary"
      subject also states: "ops/build-flow, ONE recipe line; ZERO shipped bytes, generated
       parsers byte-identical"

    before 0099d0d3:  cargo build --features generated_parsers --bin ast_pipeline
    at     0099d0d3:  cargo build --features "generated_parsers ebnf_dual_run" --bin ast_pipeline

  `parse_harness_equivalence` is gated on BOTH features. With `generated_parsers` alone it was
  never compiled, so `active_grammar_profile` was never referenced and the cold path was fine.
  Adding `ebnf_dual_run` pulled the module into the bootstrap build — and with it a reference to
  a function gated on a family parser that, at that point in the bootstrap, does not yet exist.

  ⇒ A fix that closed a REAL trap (an under-featured binary silently judging the wrong artifact)
    opened a different one, in a direction its own "ZERO shipped bytes / byte-identical" evidence
    could not see. Both halves of that claim are TRUE. Neither is about the cold path.

## WHY NOTHING CAUGHT IT — the recurrence of .4's own founding story

  * All ELEVEN hosted workflows that use the composite action are `workflow_dispatch` only
    (measured: every one of the 11 `on:` blocks), which is DELIBERATE documented policy
    (Actions minutes) — so no automatic run exercises it.
  * The one local instrument that WOULD catch it, `prepare_generated_artifacts` in
    `rust/scripts/ci_workflow_local_gate.sh`, replays the bootstrap into a tracked-files-only
    EXPORT DIR ("NOT a copy from the developer's tree") — but that gate is operator-invoked,
    not part of the automatic tier (21 doctrines + 3 cheap gates).
  * Every developer/agent run has a populated `generated/`, where the path is green.

  This is the same shape .4 recorded about its own defect: "hosted auto-triggers were paused …
  so the breaking change landed when there was no automatic run left to fail."

## BLAST RADIUS

  * README.md's Quick Start — the documented FIRST command for a fresh clone
    (`make -C rust SHELL=/bin/bash regenerate_generated_parsers`) — fails on a fresh clone.
  * All 11 hosted workflows would fail at their first step if dispatched.
  * A downstream consumer building PGEN from a clean checkout hits it immediately.
