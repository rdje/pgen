# THE TEST, stated before running it — IEEE 1800-2017 §5.7.1 governs the INTERIOR
# of ONE based literal, and names exactly which seams are open:

⭐ `unbased_unsized_literal` — ADJUDICATED CORRECT AS FUSED, NOT CHANGED.
   This is the trap of this sweep: `'0` / `'1` / `'x` / `'z` LOOK exactly like the
   unsized `'b0` twins that ARE defective, and a mechanical "add the seams
   everywhere an apostrophe appears" pass would have widened it. The LRM forbids
   that, in its own Annex A footnote, verbatim:
       "48) The apostrophe ( ' ) in unbased_unsized_literal shall not be followed
            by white_space."
   Note this is a DIFFERENT prohibition from the `'`<->base-char one: there is no
   base-format token here at all, so the value follows the apostrophe DIRECTLY and
   the only candidate seam is explicitly closed. => NO CHANGE. Widening it would
   have changed acceptance with the LRM pointing the other way.
   (Same shape as `.3.9`'s `attr_open "(*"` / `attr_close "*)"` adjudication: the
   sweep's job is to decide every member, and "correct as fused, here is the cite"
   is a real verdict, not a skipped one.)
