# `SV-CORPUS-GRAD.3.15` — the bare `generate_block` family: evidence bundle

Owning leaf: `docs/tasks/SV-CORPUS-GRAD.md` → `.3.15`.

**Verdict: the parser is CORRECT on all 25 rows and the manifest was wrong.** No parser,
grammar, generator or generated byte changes in this leaf. The movement is an
**adjudication correction**, never burn-down yield.

## The construct

IEEE 1800-2017 A.4.2 (`docs/systemverilog/2017/md/section-27-generate-constructs.md:68-127`,
mirrored verbatim by `grammars/systemverilog.ebnf:2517-2521`):

```ebnf
generate_region ::= generate { generate_item } endgenerate
generate_item   ::= module_or_generate_item | interface_or_generate_item
                  | checker_or_generate_item
generate_block  ::= generate_item
                  | [ id : ] begin [ : id ] { generate_item } end [ : id ]
```

`generate_block` is reachable **only** from `loop_generate_construct`,
`if_generate_construct` and `case_generate_item`. Neither `generate_item` nor
`module_or_generate_item` offers it. So a `begin … end` block sitting *directly* in a
generate region — or in a module body — has no production at all. It is the pre-2005
**"legacy generate region"**, and verible's own lint rule names it exactly that inside one
of the fixtures pinned here (`// verilog_lint: waive legacy-generate-region`).

The same holds in the other edition: IEEE 1364-2005 A.4.2
(`grammars/verilog_2005_lrm_extracted.ebnf:452-462`) reaches `generate_block` only from
loop/if/case, and `module_or_generate_item` (`:749`) has no bare-block alternative. The
verdict does not change with the edition.

### ⛔ Why a sweep and not the family map

`classify_rejects_valid_families.py` buckets on the **stuck line's surface text**, so it can
only see a row whose stuck line literally reads `begin : label`. It reported this family as
**20 rows** — of which one (`InsideOp/dut.sv`) is not the construct at all (it stops at an
`inside` set in a generate condition, routed to `.3.16`). Deciding the fix scope from the
bucketer would have meant fixing whatever the bucketer happened to name. The sweep decides
from the **stuck position** over all 331 rows and returns **19**, confirming the hand
adjudication exactly and adding nothing.

### ⛔ Two instrument defects found while building these, both stated rather than quietly fixed

1. **A catastrophically-backtracking regex.** The first spelling of "strip the trailing
   whitespace/comment run" was
   `re.sub(rb"(?:\s+|//[^\n]*|/\*.*?\*/)+\Z", b"", consumed)` — two quantifiers nested under
   an anchored `+`. Measured **spinning at 100 % CPU for over three minutes** on this corpus
   with **no probe subprocess running at all**: the instrument looked *busy*, not *broken*,
   and would have been reported as "the corpus is slow". Replaced by a linear backwards
   scan; the same sweep now completes in **5 s**, matching `cluster_rejects_valid.py` on the
   same file set. The tell was CPU time ≈ wall time with an empty process table.
2. **A `--manifest` resolved against the caller's cwd.** Fixed to resolve against the
   repository root (directive 12), so one command line means one thing from any directory.

## ⛔⛔ The sixth-through-eleventh rows exist only because the sweep was parameterized by lane

The leaf was cut from the **sv_2017** axis-2 worklist, and MEMORY's `next_action` names that
lane. Parameterizing the sweep by `--manifest`/`--profile` instead of hard-coding it surfaced
**6 further rows in the `verilog_2005` lane** (all iverilog), **none** of which is one of the
19 sv_2017 files. Stopping at the lane the task named would have shipped a half fix that
looked complete — and no pass-rate, cluster map or family table would have shown the gap.

## Honest bounds

1. **A `must_reject` row proves the file is invalid, not that the rest of it parses.** Each
   of the 25 stops *at* the illegal construct, so any further defect later in the same file
   is invisible to that row by construction. The residue is worked as crafted minimal cases
   in the `.9` gap loop, where the construct is the unit — the same disposition `.3.13` gave
   its four stuck-elsewhere rows.
2. **Tolerating the construct stays FUTURE and ADDITIVE.** Real tools accept it, and that is
   a real-world datum, not a conformance argument
   ([[feedback_sv_strict_lrm_compliance_default]]). Making it parse today would convert a
   correct reject into an over-acceptance defect.
3. **`t_gen_if.v` and `t_gen_duplicated_blocks_bad.v` place the block in a module body**, not
   a generate region; `t_gen_if.v` says so itself (*"Bare begin/end extension of IEEE allowed
   by most all tools"*). Same cite, since `module_or_generate_item` has no bare block either.
