# `ENGINE-UNIVERSAL-SERVICES.69`(a) SLICE 2 — PRE-REGISTRATION

Written **before** the deciding measurements ran and before any line of
`rust/src/dedicated_parse_stack.rs` was edited. Recorded because this tree has now paid
ten times for a frame inherited rather than checked (layer A's running series), and twice
in `.69` alone — `.69`(d)'s `STACK_BASE_ANCHOR_PAD_BYTES` frame is the only reason a
0.004 % overshoot was not published as a refutation, and slice 1's doubling-ladder confound
was caught only because the reservation-scaling prediction was written down first.

## What is being changed

`DEDICATED_PARSE_STACK_BYTES = 256 * 1024 * 1024` is a literal a developer typed. `.69`(a)
owes a default derived from a real host quantity. The change makes the resolved reservation

    reservation = min( REFERENCE , max( FLOOR , host_physical_memory / SHARE_DIVISOR ) )

with `SHARE_DIVISOR = 64`, `REFERENCE = DEDICATED_PARSE_STACK_BYTES`, `FLOOR =
MIN_DEDICATED_PARSE_STACK_BYTES`.

## The frames I am naming, so a result cannot inherit them silently

1. **THE ROLE.** `DEDICATED_PARSE_STACK_BYTES` is read in TWO places with TWO meanings — as
   the default reservation, and as the SCALING REFERENCE in
   `scale_sample_depth_to_reservation`. A change that moves the default without splitting the
   roles moves the reference too.
2. **THE DIRECTION.** A derived default is a per-host number, so the accept set becomes a
   per-host property. That is what the mandate asks for and it is also how a corpus number
   silently becomes host-dependent. The two readings are not distinguishable from a green run.
3. **THE COST OF THE UPWARD HALF.** Raising the reservation raises the depth at which the
   `.78` ceiling ladder crosses, and crossing cost is Θ(depth²) (`.68`). A test whose runtime
   is a function of the CI host's RAM is a defect even while it is green.
4. **THE HOST IS BUSY.** Load average 4.28, an unrelated `rustc` at 27 % CPU in a sibling
   repository. Every wall-clock or peak-RSS reading taken in this slice is INDICATIVE ONLY
   (layer A: never measure peak RSS on a busy machine). Deterministic columns — byte counts,
   depths, causes, derivation arithmetic — are load-independent and are what the claims rest on.

## Predictions (each falsifiable, each with the observation that would refute it)

- **P1 — THE DESIGN POINT IS REPRODUCED.** `derive(16 GiB) == 268 435 456` EXACTLY. The
  shipped literal is not replaced by an unrelated number; it is explained as the value the
  law already produces on a 16 GiB host. REFUTED by any other value.
- **P2 — THIS HOST IS BYTE-IDENTICAL.** This host has 25 769 803 776 B (24 GiB) ⇒ the
  unclamped share is 402 653 184 B (384 MiB), above `REFERENCE`, so the cap saturates and the
  resolved reservation stays **268 435 456**. ⇒ the shipped accept set on this host does not
  move at all. REFUTED if the probe reports any other reservation with no env override.
- **P3 — THE LAW BITES BELOW THE DESIGN POINT.** `derive(8 GiB) == 134 217 728`,
  `derive(12 GiB) == 201 326 592`, `derive(6 GiB) == 100 663 296` (the floor),
  `derive(4 GiB) == 100 663 296` (the floor), `derive(1 GiB) == 100 663 296` (the floor).
  The floor dominates below 6 GiB; the derivation is live only in the 6–16 GiB band.
- **P4 — THE REFERENCE MUST NOT TRACK THE DEFAULT, AND THE CONTROL CAN GO RED.** If
  `scale_sample_depth_to_reservation` scaled against the derived default rather than the fixed
  reference, a host deriving the floor would satisfy `reservation >= reference` and take its
  first sample at the full 4 096 frames on a 96 MiB reservation — which `.79` MEASURED as an
  `rc 134` SIGABRT between 3 550 and 4 034 frames. PREDICTION: the RED control reproduces that
  arithmetic (`4096 × 25 874 > budget(96 MiB)`). REFUTED if the control passes.
- **P5 — THE HOST READING AGREES WITH AN INSTRUMENT I DID NOT BUILD.**
  `host_physical_memory_bytes()` returns exactly what `sysctl -n hw.memsize` prints
  (25 769 803 776). REFUTED by any disagreement — which would mean the derivation reads a
  different quantity from the one it names.
- **P6 — ZERO GENERATED BYTES.** All 11 generated parsers re-derive byte-identically. The
  change is confined to `rust/src` and touches no grammar, no codegen and no emission.
- **P7 — THE CAP IS LOAD-BEARING FOR AN EXISTING TEST, AND I EXPECT TO BE ABLE TO SHOW IT.**
  `stack_probe_names_the_terminal_refusal_after_a_real_spend` burns
  `budget/2 + budget/8` and skips when that exceeds `MAX_SAFE_BURN_BYTES = 200 MiB`.
  At the capped 256 MiB that is 150 MiB ⇒ the body RUNS. Without the cap, this host's
  384 MiB would make it 225 MiB ⇒ the body would be SKIPPED while the test stayed GREEN.
  PREDICTION: both arithmetics hold as stated. ⇒ the uncapped design would have made an
  existing lock vacuous on every host above 16 GiB, silently. REFUTED if either figure differs.

## What this slice deliberately does NOT claim

- It does **not** claim the 1/64 share is DERIVED. It is a POLICY, pinned by the
  no-regression anchor in P1, and it is documented as a policy exactly as `.79` re-cast
  `MIN_DEDICATED_PARSE_STACK_BYTES` from a proof into one. The measurement that would let the
  share be derived — the total process footprint at full stack spend — rests on a quantity
  `.84` records as NOT ATTRIBUTED (peak RSS is in neither the arena nor `peak_live`), so
  deriving the share today would put an unmeasured term inside a safety bound. `.84` is the
  leaf that removes it.
- It does **not** deliver the upward half of the mandate (a bigger host accepting deeper
  input). That is capped here, priced in frame 3 above, and owned by a named leaf.

## ⛔ SCORING CORRECTION (`-0158`, added after a director challenge)

**P1–P7 all confirmed and all still stand.** What did NOT come from this pre-registration is the
slice's headline finding, and that is the point worth recording.

Frame 1 above named THE ROLE (the constant serving as both default and scaling anchor) and the
design was built on it correctly. But no row here predicted anything about **the mutation battery's
own coverage**, and that is exactly where the slice went wrong: a control came back green, I
diagnosed it as *"unfalsifiable on this host"* and published that to the director — and the
diagnosis was refuted in one command (`PGEN_PARSE_STACK_BYTES` either side of the reference makes
the lock fail both ways).

⇒ **the frame this pre-registration was missing is THE CONFIGURATION**: a mutation is only a
control in a process where the defect it names can EXIST, so before reading a green mutation as a
statement about the lock, enumerate the configurations in which the mutated program actually
differs from the correct one. Two of my seven mutations needed a non-default one; I ran none.

This is the eleventh entry in the running series of pre-registration failures kept in layer A, and
it is the second of them (after `-0132`'s PROVENANCE) where the refuting evidence was already
inside my own artifact.
