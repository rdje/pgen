## The tool — LAZY WINNER-ONLY MATERIALIZATION

**The problem it addresses.** PGEN's multi-branch rules are a *tournament*: under the default
`longest_match` policy the engine tries every alternative and keeps the longest successful match.
The naive (sequential) implementation does the full per-branch WORK — the return-annotation JSON
fold (`ParseContent::to_json_value`) + a `raw_content.clone()` — for **every** branch that parses,
then throws away all but the winner's ("fold 24, keep 1" for a 24-branch `atom`).

**The elegant idea.** The winner is selected from cheap metadata alone — `candidate_end` /
`candidate_priority` / `branch_predicate_blocked` — never from the transformed output. So:
*decide the winner first from the cheap signal, and run the expensive materialization ONCE, for
the survivor only.* Losing branches materialize nothing.

**The realization that keeps it byte-identical** (the part the director called elegant):

- Compute `should_take` (the tournament decision) **before** the transform — it has no dependency
  on the transformed value, so this reordering is free.
- Run the transform **only inside the `should_take` gate**, and crucially **before the position
  rollback** (`parser.position` still `== candidate_end`), so `$text` / MatchedText still slices
  `input[parse_start..candidate_end]` exactly as the eager placement did (the BRANCH-BROADCAST-FIX.3
  ordering constraint is preserved *for free*, not fought).
- Capability gate: only rules with **no branch-phase `@predicate`** are eligible (a branch
  predicate is the one other consumer of the transformed value). `rule_has_no_semantic_annotations`
  is the sound over-approximation.

Byte-identical **by construction**: the winner's deferred transform yields the same output as the
eager one (same `raw_content`, same `parser.position`); a loser's transform was discarded anyway,
so not running it is output-neutral. This was **proven decisively** — `parse_harness_equivalence_gate`
(interp↔generated byte-identical, all 11 grammars, seeds 0/7/42), combinator 27/27 (incl. the
`a|ab` longest-match discrimination), semantic 36/36, regex cert `fully_certified` UNKNOWN=0 spf
`0/1/1`, and a PCRE2 fix-vs-nofix per-case diff **empty** over 2188 corpus cells (`1878/310/262/48`).

**The general principle (the reusable part).** *Explore candidates in LOCKSTEP (in parallel), defer
each candidate's expensive per-item work, and materialize once for the survivor — instead of
re-doing the work sequentially per candidate and discarding most of it.* This is the same principle
that underlies the entire `.5.d` lockstep-simulation road (re2c / Hyperscan advance all live
branches together and only the winner produces output), and it generalizes far beyond regex — it is
a tool for any tournament / speculative-evaluation / multi-candidate site in PGEN. PGEN has a long
way to go feature-wise; this is banked, not discarded.

## The lesson — SUBSTITUTE levers vs COMPLEMENT levers

The reason `.5.d.2` was reverted despite being correct and elegant:

> **First-set predictive dispatch (`.5.c.2`) and lazy-winner-only materialization (`.5.d.2`) are
> two DIFFERENT solutions to the SAME observable problem — the cost of the losing branches. They
> are SUBSTITUTES, not COMPLEMENTS.** First-set eliminates a losing branch *before* it is tried
> (it never parses or transforms); lazy eliminates a losing branch's transform *after* it parses.
> Since `.5.c.2` (the −75% lever) already removes those branches up front, `.5.d.2` arrives to find
> almost nothing left to defer — so it is **byte-identical but speed-NEUTRAL**.

Measured proof: a decisive 7-round drift-controlled `regex_perf_probe` geomean-of-mins, both release
fat-LTO binaries (distinct sha256, nofix regen confirmed eager), fix ≈ **75.5 µs** vs nofix ≈
**75.9 µs** — heavy overlap, per-round sign flips, inter-round variance exceeding the gap. No
decisive separation ⇒ no win.

**The durable rule:** *before landing a speed lever, ask whether an already-landed lever attacks the
SAME observable cost. If it does, the second lever is a substitute — its marginal gain is likely
~zero, and it must be measured against the current baseline (not the pre-first-lever baseline)
before it earns its keep.* The decisive drift-controlled before→after measurement is what caught
this — a lever that "obviously should help" delivered nothing because a prior lever already owned
its cost. (Same discipline as [[project_uvm_memory_not_the_memo]]: profile/measure, don't infer.)
